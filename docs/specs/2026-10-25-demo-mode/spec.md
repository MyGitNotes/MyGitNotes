# Demo mode (community)

A deployment can let visitors try the app on public content, whether or not they are signed in. They edit, commit and restore versions in their own browser; nothing they do reaches the server. A signed-in person gets the same demo as a visitor, and their own account, notes, drafts and session stay untouched (see [A signed-in browser](#a-signed-in-browser)). This is the community part; an edition supplies the repository and the rules for who sees it (the Pro edition vendors its own).

## What a deployment supplies

- A `WorkspaceConfigSource` with `demo: true`. The session probe (`GET /api/auth/session`) then answers `demo: true`, which is how the web app learns the deployment offers a demo.
- For a visitor who is not signed in and sent the demo cookie, a member marked `demo: true` (`WorkspaceMember.demo`). `GET /api/workspace` copies the flag to `RepositoryStatus.demo` and keeps `write: false`.
- Nothing else changes server-side: every write route already refuses a request without a session (`signedIn`) or without `write` on its repository, so a demo request cannot change the repository, its manifest, its assets or its Agent documents, and `…/testing/memory-edition-source` can stand in for the edition's repository in tests.
- For a signed-in person, the server's own rule: a request made by a **demo page** (see below) loses its credentials first, so the edition's configuration source sees a visitor who sent the demo cookie. A configuration source that sets `demo: true` gets this from `createApp`; an edition that composes another app around it (Pro's `outer`) mounts `demoPageCredentials()` ahead of its own routes.

## The demo cookie

`mygitnotes_demo` holds only a language (`en` or `zh-tw`), is written by the web app on a `/demo` page (`Path=/; Max-Age=86400; SameSite=Lax`, `Secure` on https) and carries no authority. `demoLanguage(request)` (`@mygitnotes/core/demo`) reads it and ignores anything else; the configuration source decides what the language selects. The cookie is `Path=/`, so a browser sends it from every page; a signed-in request that does not come from a demo page ignores it, as before, and one that does is a visitor's (see [A signed-in browser](#a-signed-in-browser)). `demoNotebooks(config, language)` keeps, for each scenario (a notebook id without its `-en` or `-zh-tw` suffix), the notebook in the asked language, else its `-en` twin, else the first, and moves `default_notebook` to the kept twin. A page keeps working when the cookie no longer matches it (it expired after 24 hours, the visitor cleared it, or another tab chose the other language): the server then answers 404 for the notebook, and `readNote` raises that as a plain error, not as an `ApiError` 404, since a demo repository never changes and its note cannot have been moved or deleted. The editor shows the error and makes no conflict draft, so Changes never lists a note nobody edited as a conflict.

## Web app

- `/demo` and `/demo/<scenario>` open the demo: the router's basename is `/demo`, so navigation, reloads and shared links stay there. The app's own pages (`APP_ROUTE_PATHS` in `lib/routes.ts`: Notes, Files, Graph, Settings, Agents and the former Screen addresses) keep their addresses under `/demo`; a first segment in `APP_ROOT_SEGMENTS` (also `index`) is never a scenario. `/:scenario` is resolved after the workspace loads to the notebook whose local id is the scenario or starts with `<scenario>-`; an unknown scenario opens the default notebook and the banner says so. The scenario opens the notebook's best view: when the repository's Focus file (`.github-notes-focus.yaml`) lists a named Focus for the notebook, the first one in file order (`/notebooks/<notebook>?focus=<id>`, so the demo address `/demo/trpg` becomes `/demo/notebooks/demo~trpg-zh-tw?focus=trpg-zh-tw-table`), so a visitor lands on the arranged notes side by side; otherwise the notebook's `index.md` (the folder index the notebook page already links, found at the notebook root) when it has one, a guide with e.g. a "What to try" list; without one the notebook's page. The choice waits for the Focus file to load, and a Focus file that fails to load names no Focus. The demo repository's author picks the entry view by ordering the Focuses in the file; no manifest field is involved. A visitor whose Focus view for the notebook holds a tab in the current Focus or a named Focus shown last (`hasStoredFocusView`) gets the notebook's page, which restores that view; an address that names a note, and any reload, are not `/:scenario` and are left alone.
- The cookie's language is the app's, except when the address names a notebook or scenario of one language (`/demo/notebooks/demo~trpg-zh-tw`, `/demo/trpg-en`; `addressDemoLanguage`): then that language is written first and the app switches to it, so a link to one language's notebook opens it whatever language the app was in (0.13.9). After that the person's own choice of language rules.
- `WorkspaceGate` writes the cookie before anything else, then sends two session probes at once (see [A signed-in browser](#a-signed-in-browser)) and shows "The demo is not available" (no `demo` in the probe), the referrer notice (a signed-in browser whose demo page the server did not recognise, or a workspace answer that holds any repository that is not the demo's), "The demo needs cookies" (no demo repository came back, with a retry), or the workspace with no sign-in screen. The notices are drawn by the same setup screen as the sign-in, so an edition's `WebFeature.signInIntro` words their left panel too. Outside the demo, a workspace answer that lists a `demo` repository is a session that ended in this tab and is reported as such.
- Changing the language in the demo rewrites the cookie and opens the same scenario again.
- A `DemoBanner` above the workspace says that edits and commits stay in this browser and are cleared 24 hours after the first change (with the time left once there is one), offers Reset demo and a call to action (`WebFeature.demoCallToAction`, default "Sign in to keep your own notes"; "Open my notes" for a browser that is signed in, which links to `/`). A call to action renders inside the demo context, so `useDemo()?.signedIn` (exported from `@mygitnotes/web/kit`) tells it which to offer.
- The header shows no account controls in the demo (`AccountControls`, `AuthControls`), whether the edition replaces them or not: a demo page signs nobody in or out, and the banner is the way to the person's own notes.

## A signed-in browser

The demo and the person's notes share an origin, so one browser can hold a session and open `/demo`. The demo then must not read or write anything of the person's, and leaving it must land them in their own notes, signed in.

**The page a request comes from.** The server treats a request as a **demo page's** when its `Referer` is an http(s) address whose path is `/demo` or under `/demo/` (`demoPageRequest`, `@mygitnotes/core/demo`; only the path counts, never the origin). A browser sends the `Referer` on every request a page makes (`fetch`, `<img>` and `<video>` for `/raw-assets/*`, both event streams, downloads), which a header the app adds would not cover; it is per document, so a tab on `/` and a tab on `/demo` keep their own roles; and a same-origin request carries the full path under the default policy and the server's `Referrer-Policy: same-origin`. A cross-site page cannot name a `/demo` path, and one that did would only get a request with less authority.

**Matching only removes.** `demoPageCredentials()` (`apps/local-server/src/demo-page.ts`, exported from `edition.ts`) is `createApp`'s first middleware when `configSource.demo` is set, so a deployment without a demo is unchanged. For a matching request it:

1. rewrites `req.headers.cookie` to the demo cookie alone, rebuilt from the language `demoLanguage` reads (everything else is dropped, so a cookie an edition adds later is dropped too), and deletes `authorization`; `req.rawHeaders` is rewritten the same way, so a reader that parses it afresh finds nothing more;
2. remembers the request (`isDemoPage(req)`), which makes mounting it twice harmless;
3. removes `Set-Cookie` from the response just before its head is written (`res.writeHead`, whether the route used `res.cookie`, `res.setHeader`, `res.append` or a `writeHead` headers argument), so no demo-page answer sets, renews or clears the person's session, sign-in state or workspace choice.

Behind it, `refuseDemoPageSignIn` answers 403 `{ code: 'demo-page' }` to everything under `/api/auth` but `GET`/`HEAD /session`: without it, `POST /api/auth/logout` would clear the person's cookie even with no cookie sent, and an OAuth start would replace their session. The session probe adds `demoPage: true` (from the request alone, never from a session). Everything downstream (identity, the configuration source, `requestWorkspace`, rate limits, `/mcp`) sees a request with no session and the demo cookie, so it is a visitor's, and the write routes refuse it as before.

**Fail closed.** If something strips the `Referer` (an extension, a policy), the server never sees a demo page, the probe from the demo page answers the person's own session, and the gate shows a notice instead of opening: the person's notes never render under `/demo`.

**The gate's two probes.** `DemoGate` sends, in parallel, the demo probe (`fetch('/api/auth/session')`, with the page as its Referer; it answers `demo`, `demoPage` and `authenticated: false`) and the account probe (`fetch('/api/auth/session', { referrerPolicy: 'no-referrer' })`). The account probe is the only request a demo page makes as the person, and its answer feeds only `signedIn`, which the banner shows. The gate then:

- shows "unavailable" when the demo probe has no `demo`;
- shows the referrer notice (`demo.referrer`: the browser did not tell the site that this is the demo page, so it cannot open while signed in; it offers "Open my notes" and a private window) when the demo probe is signed in, or the account probe is signed in and the demo probe has no `demoPage`;
- reads the workspace and shows the same notice if the answer holds any repository that is not the demo's (`useWorkspaceSync` tightens its refusal the same way, and `commitGroup` still refuses a non-demo repository on a demo page), "needs cookies" if it holds none, and otherwise opens;
- wraps the workspace in `DemoProvider` with `{ ...demo, signedIn }`.

**Browser storage.** The demo's data is namespaced already (`demo:<repository id>` in the draft scope, document drafts, Focus views, history stash, local commits and the 24-hour records), so no key changes, and the demo tab and a tab of the person's notes never share one. The `storage` listeners (`use-workspace-sync`, `use-workspace-document`, `use-note-focus`, `local-commits`) each answer to their own key, so a write in one tab changes no state of the other. The offline screen is where the namespaces could still meet: a tab of the person's notes counts none of the demo's drafts (`offlineDrafts`), and the demo lists none of the person's titles and counts only its own. The UI language, theme, sort order, panel widths, graph appearance and table width belong to the browser and not to notes, so what is chosen in the demo applies to the other tab too.

**Links.** "Open original" of an asset on this site keeps `rel='noopener'` and drops `noreferrer`, so the new tab asks for the asset as the demo page does; one on another site keeps both.

## What is local and what is not

`editable(repository)` is `write` or `demo`. Wherever an action ends in a working change or a commit it asks `editable`; everything the server would change stays on `write`.

| Local in the demo | Not available in the demo |
| --- | --- |
| Note content, title of a never-committed draft, status, tags, metadata; new notes; delete to trash; Kanban and list status changes | File moves, renames and new folders; asset upload, move and delete; the R2 panel |
| Focus layouts and other workspace documents, as document drafts | Bulk tag rename, merge and delete; bulk moves; folder manager; outline import; Import legacy bookmarks |
| Working changes listed in Changes and committed; commit with a version name; restore from history | Manifest editing; Settings beyond Preferences (theme, language, editor); the agent panel; AI polish; publish rows; Gists |

Actions the demo does not offer are hidden, not shown disabled (the app's pattern for a repository that cannot change files). The Info tab does not call a demo repository read-only (`readOnlyReason`). A demo page whose workspace answer holds a repository that is not the demo's (the server did not take the page for the demo's) shows the referrer notice instead of the person's own repositories, and `commitGroup` refuses any non-demo repository there, so "Commit in this browser" and a remote commit never meet.

## Local commits

A commit made in the demo is recorded in `localStorage` under `gh_notes_local_commits:<draft scope>` (`local-commits.ts`):

- one entry per commit with a 40-hex id (SHA-1 over the parent, date, message and changes), its parent (the server head, then the previous local commit), the stored text of each changed note (what the server's `commitNotes` would write, via `serializeNoteFile`) or its deletion with the server's note it replaced, the changed workspace-document pages, and the version it recorded (numbered after the repository's versions);
- at most 200 commits and 1 MB (UTF-8 bytes) per scope; a commit past either is refused before anything is written ("This demo keeps at most 200 commits (1 MB) in your browser. Reset the demo to keep going.").

`useWorkingNoteCommit` takes this path for a `demo` repository (`commitLocally`) and posts nothing.

A commit moves the committed note under every open editor of it. An editor whose text is then the committed note (ignoring the timestamps the commit stamped) takes that note as its base (`useNoteEditorSession`, on `remoteBase`); otherwise it keeps the base it had. Without this the base stays the note the editor opened on, and the check that reads the committed note ("remote") a minute later merges the earlier commit's changes into a text restored from history: the "Remote changes merged into this draft" notice with the old line back, or a conflict. The head never moves in the demo, so the committed note is the only thing a draft can be merged against.

Reads see the commits in two places only. The query overlay is `composeCommitted(committed, workingChanges)` in `setNoteQueryScope`: a committed note overlays server answers like a draft whose base is the server's note, so counts subtract it; a working change over it keeps its text and takes the same server base. Direct reads (`readNote`, `useNoteLookup().committed`, `findCommittedNote`, a workspace document's page) take the committed note.

History (`history-api.ts`): page 1 of a note's history lists its local commits above the repository's, marked "In this browser", with their versions (`HistoryPage.localCommits`); a local commit id or blob is read from the browser, anything else from the server; a local commit that did not change the file shows the repository head's text. The version panel offers "Commit as a new version" when `writable || localCommits`; marking, editing and deleting a version of a repository commit stay `writable`. Compare and restore work on the point texts and need nothing else.

## 24 hours

A demo repository keeps its browser data under its own namespace (`storageId`: `demo:<repository id>`), in the draft scope, the document drafts, the Focus views and the history stash alike. A signed-in person's repository that has the demo's id or notebook alias therefore never shares, shows or loses those keys, and the sweep matches only the demo's namespace, never a notebook alias.

`demo-storage.ts` keeps `gh_notes_demo:<draft scope>` = `{ firstWrite, base, repository, alias }` (`repository` is the namespaced storage id; `alias` names the repository's notebooks by key), written by the first persisted demo write the visitor made: working changes, editor drafts, document drafts, the history stash, a layout change of the (current) Focus and a local commit. Merely opening a notebook does not start the clock.

Focus view state the visitor did not choose (the Focus last shown, the active pane, pane sizes, the dock) is kept too, but is not a change. A scope with no clock gets `gh_notes_demo_view:<draft scope>` (same shape, written by the first such write) instead, and its Focus views are swept 24 hours after it; when a change starts the clock the view record is dropped and the clock rules the views. So no key of a demo scope outlives 24 hours, and the banner's "24 hours after your first change" stays true: view state is only ever cleared earlier than that, never later.

A Focus view is kept only once the workspace says which repository serves its notebook; until then it is neither read nor written, so no `github-notes:focus-view::<notebook key>` key (no repository in its name) is made. A scope's sweep also removes such a key left by version 0.11.0 when its notebook key starts with the scope's alias (any such key when the record predates `alias`).

- `expireDemoData()` runs at every app boot, on any route, before anything renders, and before each demo write; a scope whose record is 24 hours old loses every key it made (working changes, editor drafts and their conflict keys, document drafts, Focus views, stashed texts, local commits, the record). A write that finds its scope expired clears it, reloads the page and writes nothing (`demoExpired`/`noteDemoWrite` answer false, `appendLocalCommit` throws `DemoExpiredError`); every writer asks before it reads what it would write over, so expired data never comes back and the clock does not restart.
- When a deploy moves the demo repository's head, the workspace load finds the record's `base` differs and clears the scope; the banner says the demo was updated.
- Reset demo clears the scope at once. Demo scopes are not recorded as opened scopes for the offline screen, and the screen counts them apart from the person's drafts.
- A browser runs no code while the site is closed, so data stays on disk until the next visit to the app after the 24 hours, and is removed then.
