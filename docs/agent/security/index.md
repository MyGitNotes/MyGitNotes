# Security & Guards

MyGitNotes handles local filesystem and Git operations with defense-in-depth boundaries.

## 1. Path Traversal & Symlink Guards

All file paths received by the MCP server or local API bridge are validated through `packages/core/src/path-guard.ts`:

- All relative paths are normalized and resolved against the repository root.
- Paths containing `..` or attempting to escape the repository root are rejected with an explicit error.
- Symlinks pointing outside the repository root are forbidden.

## 2. Branch Guards

- Write operations on user notes (`notes/**`) are only permitted when the active branch is a user workspace branch (typically `main`), preventing accidental mutation of product code on `core`.
- Updates to product source files are guarded against overwriting user notes.

## 3. Secret Safety

- Secrets such as API keys and tokens must never be written to Git-tracked files.
- `.env` files are ignored by Git.
- Local MCP stdio operates within the local user process boundary and does not expose open network ports.
- The local HTTP bridge binds to `127.0.0.1`, validates loopback hosts and origins, and restricts workspace mutations to `main`.
- Hosted `/mcp` uses HTTPS and a service-issued bearer grant scoped to its audience, the person and site it was made for, and their persistent account credential; the grant is verified before any workspace is resolved, and the request reaches the configuration source without its browser cookie. A grant made before person-bound grants reaches only its original repository, and only while that repository is a visible member. Write grants additionally require the selected provider's push permission and the `main` workspace branch.
- Provider tokens stay in encrypted server records. Browsers receive opaque HttpOnly session cookies. Hosted records use a durable Redis store; logout deletes the browser session.
- The lightweight mode (`MYGITNOTES_STORAGE=cookie`, or Vercel without Redis) keeps no server records: the session, provider token and refresh token included, is sealed with `SESSION_SECRET` (AES-256-GCM) into the HttpOnly, `SameSite=Lax` session cookie, and so are the OAuth state and PKCE verifier between redirect and callback. Logout clears the cookies; a stolen cookie stays valid until its token expires, since the server cannot revoke what it does not store. GitHub refresh tokens are single use, so a refresh that fails signs the visitor out. It signs in with GitHub only and offers no agent grants. Where a deployment sets no repository (`MYGITNOTES_SOURCE=github` alone), the visitor's chosen repository and branch are sealed in their own cookie and every read and write goes through their token, so the deployment never reaches a repository the visitor's token cannot. New agent grants have no TTL and use owner-authorized manual revocation; legacy session-linked grants retain their original lifecycle.
- Remote reads share a content-addressed cache keyed by repository and Git object id. A request only looks up object ids listed in the tree it fetched with its own authorization, so cached content reaches nobody who cannot already read it. Values are verified against their Git object id before they are stored. The per-process HTTP cache stays scoped to one authorization.
- Gist publishing (`/api/gists`, GitHub workspaces only) creates and deletes secret Gists on the signed-in account with its own OAuth token. It sends only the note body the browser submits; the Gist id lives in the note's `gist` frontmatter. `/api/notes/commit` and `/api/notes` push each committed note that names a Gist to it after the commit succeeds; a failed push is reported per note and never undoes the commit. A secret Gist is unlisted, not private: anyone with its URL can read it.
- An edition's identity may accept a bearer on `/mcp` that this server did not issue (`IdentityService.bearerGrant`); the community identity accepts none. The identity alone verifies it. The server asks only about a bearer in the `Authorization` header that is not shaped like a stored grant, refuses an answer that is not a complete grant, holds the answer to the deployment's site and to its `write` flag, removes the header from the request before the workspace is resolved, and runs the call with the credential the identity gives its grants. The bearer is never stored, used as a record id, logged or sent to a provider; a failed verification logs the error's class name only, and answers the same 401 as a missing grant.
- A commit's author is named by the identity alone (`SignedIn.author`, a grant's `author`), never by a request body, header or tool argument; the community identity names none, so the provider records the token's account. A check-in of a live note is the one commit that also follows `SignedIn.live` ([Live editor](#4-live-editor)). A name or email with a line break, `<`, `>` or a control character is refused before any provider request (400), so neither an author nor a `Co-authored-by` co-author can add a header, an identity or a trailer to a commit. A provider does not verify an author it is given, so an identity that sets one vouches for it.
- Credential-bearing MCP URLs and Bearer headers resolve the same grant. Grant lists contain record digests and metadata; token values are shown only at creation.
- A demo request (`WorkspaceMember.demo`) is a signed-out request: it gets no write permission from any route, so nothing it does reaches a repository, a manifest, an asset bucket or a Gist. The `mygitnotes_demo` cookie holds only a language from an allowlist and grants nothing. A signed-in browser can open the demo without lending it its session: a request whose `Referer` is a demo page (`demoPageRequest`) loses every cookie but the demo cookie and its `Authorization` header before any code reads them (`demoPageCredentials`), receives no `Set-Cookie`, and cannot reach a sign-in or sign-out route; the match can only remove authority, and when the `Referer` is missing the web gate refuses to open the demo instead of showing the person's notes under it. The visitor's edits and commits live only in their browser (`localStorage`), bounded to 200 commits and 1 MB per scope, and are removed 24 hours after their first change.
- Public remote reads use anonymous requests. Private reads use the authenticated user's provider authorization. Responses containing workspace data are private/no-store.
- Browser Markdown is sanitized before rendering. Raw assets are restricted to workspace asset paths and served with a restrictive content security policy.
- R2 assets (`r2:<key>` references) are served by `/r2-assets/<key>?note=<path>`: the requester must be able to read that configured note with their own workspace permission, and the note must reference the key; only then does the server redirect to a 5-minute presigned URL. R2 credentials come from deployment environment variables and never reach the browser. `/api/r2*` management routes (list, preview, presigned upload, folder creation, move, delete) require the same write capability as file mutations, accept any valid key in the configured bucket (notes may reference any key, so management is not confined to a notebook prefix), and hand the browser only presigned URLs; move rewrites referencing notes as one workspace mutation.
- A local workspace answers `/r2-assets` from the checkout's R2 cache (`MYGITNOTES_R2_CACHE_DIR`, else `.cache/r2-assets`, which `.gitignore`, `.vercelignore` and `.dockerignore` leave out) before it asks the bucket, under the same check: the note is a configured note the requester reads, the note references the key, and the key lies in the asset scope when the request has one. A cached object is therefore never served to a note that does not reference it. Cache files are named by the SHA-256 of the key, so no part of a key names a path; an entry is served only when it is a regular file (a link is refused) whose size and recorded key match, and a write goes through a new file renamed into place, so a partial download is never served. A miss reads the object through a presigned URL with no credential header; `--out` of `pnpm r2-download` writes `<folder>/<key>` through `resolveSafePath`, so a key cannot leave the folder. Objects are answered with `Content-Security-Policy: default-src 'none'; sandbox; frame-ancestors 'self'`, as raw assets are, and by type only as the previewable types (no HTML or SVG) or as an attachment; the global `X-Frame-Options: DENY` is lifted so the inline preview frame works, and a PDF drops `sandbox` (the browser's PDF viewer refuses a sandboxed document) while keeping `frame-ancestors 'self'`. The cache is trusted local state: a file in `.cache/r2-assets` (for example one force-added to a cloned repository, which `.gitignore` does not stop) is served as that object, with no bucket request, to a note that references its key; it is keyed by object key alone, so it assumes one bucket per checkout, and a local delete or move of an object (the R2 manager, MCP `delete_asset`) forgets its entry.
- A local checkout without bucket keys may read objects through a hosted deployment: `MYGITNOTES_R2_REMOTE_URL` and an agent token in `MYGITNOTES_R2_REMOTE_TOKEN` (`hostedR2Source`). The token is read from the environment only, sent in the `Authorization` header only to that deployment's `/mcp` (refused unless the URL is `https`, or `http` to a loopback host; a redirect is refused so the token cannot follow one), never to an object URL, and never written to the cache, a report or a log; a refusal's body is not repeated in the error. The deployment decides what is answered: hosted `download_assets` returns 5-minute presigned URLs only for keys its own copy of the note references inside the grant's asset scope, at most 50 per call, and the client keeps only keys it asked for whose URL is `https` to a host that is not this machine (`localhost`, `*.localhost`, `127.0.0.0/8`, `::1`) or a private, link-local, shared, reserved or multicast address literal (IPv4, IPv6 and IPv4-mapped), so a hostile deployment cannot aim the local read at a local service or a LAN address; a DNS name is not resolved, so a name that resolves to a LAN host is not caught. Only a deployment on this machine may answer `http` URLs on this machine (a local stand-in bucket); objects are read with `redirect: 'error'`, paging stops once every asked key is found, and a `/mcp/<token>` tail pasted into `MYGITNOTES_R2_REMOTE_URL` is dropped. Agent-driven downloads are bounded: local `download_assets` caches at most 64 MiB per object (the view cap; `pnpm r2-download` is the explicit way to cache any size) and the browser archive holds at most 512 MiB.
- `.vercelignore` excludes local notes, secrets, session files, local source settings and the local R2 cache from uploads.
- The agent panel (`/api/pi/*`, local mode only) bridges the browser to a `pi --mode rpc` process that runs as the local user and can execute any command. Every route and the `/api/pi/ws` socket require a loopback Host and, when present, a loopback `http:` Origin; the socket always requires one. Through `pnpm dev:remote`, which reaches the app over Tailscale Serve, the bridge also admits the tailnet login that owns this machine (`MYGITNOTES_REMOTE_OWNER`) from the dev:remote origin: Serve sets `Tailscale-User-Login` on each proxied request, replacing any client value, so other tailnet users and tagged devices are refused even though they can open the notes. The socket forwards only the commands the panel uses (prompt, steer, follow-up, abort, queue clearing, new session, state, messages and extension dialog answers). Pi starts only in an agent workspace the request names by repository and folder: the repository root (the default is the default repository's), or a folder that may be a workspace (a notebook root, its ancestors, or a visible folder inside a notebook) and holds an `AGENTS.md`; it must be an existing directory inside the user's home directory. A start may name a session file to resume; the bridge passes it to Pi's `--session` only when it is an existing `.jsonl` file inside the home directory whose session header records that same folder, and otherwise Pi starts a new conversation. The bridge never passes `--approve`: Pi makes the project-trust decision itself (an extension's `project_trust` handler, then `~/.pi/agent/trust.json`, then `defaultProjectTrust`, which skips project resources in RPC mode when it is `ask`), and a bundled command-line extension (`pi-trust-extension.mjs`) reports that decision so the panel can show it. The process starts in the background when a local workspace loads, outlives sockets and page reloads, and ends only when the user ends it, switches workspaces, or the server stops. The assistant dock and its toggles are hidden when the server cannot find Pi (`MYGITNOTES_PI_COMMAND`, or `pi` on PATH).
- The Typst preview (`/api/typst-preview/*`, local mode only) runs code from the workspace's `node_modules`, so it answers whom the agent panel answers (`agentClientAllowed`): a loopback Host and loopback Origin, or through `pnpm dev:remote` only the tailnet login that owns this machine; the dev:remote origin alone is not enough. What it runs is fixed: this server's Node with the `bin` of the first `node_modules/thesis-toolkit` at or above the project's `thesis-toolkit.json` (never above the worktree root, never `npx` or a PATH lookup), then `compile <project> <target> --output <file>`, without a shell. The project and target must equal directory entries just read from disk and may not start with `-` or `.`; the output file is the server's; a request supplies only the note path, which passes the local path check and picks the project, and a target that must be one the project has. `thesis-toolkit.json` must hold exactly `root`, `projectsDir` and `bibliography`, and each of them, the configuration file, the project directory and each `main.typ` must resolve inside the worktree, or the note has no project. The run gets an allowlisted environment (`PATH`, `HOME`, `USER`, `LANG`, `LC_ALL`, `TMPDIR`, `XDG_CACHE_HOME`, `XDG_DATA_HOME`, `TYPST_PACKAGE_PATH`, `TYPST_PACKAGE_CACHE_PATH`), so `SESSION_SECRET`, provider tokens and `MYGITNOTES_*` never reach workspace code. A run is its own process group, which is signalled whole (the toolkit and its `typst`): SIGTERM after 60 s, then SIGKILL after 3 s, and SIGKILL when the server exits or is signalled; its log is cut to the last 64 KiB. PDFs are written to a temporary directory outside the worktree, removed when the server ends, and served only for the project and target of a note the request may read.

GitHub Enterprise site URLs are deployment settings too (`MYGITNOTES_GITHUB_URL`, or `url` on a `github` source). The sign-in realm, REST and GraphQL calls, Gist publishing, the shared-cache keys and the process caches follow that site, and a github.com source keeps the realm, credential ids and agent grant owners it always had, so one site's session or grant never authorizes another. An archive download is followed only to that site's own codeload, never with the user's token. Core updates act only on the deployment's product repository (`MYGITNOTES_PRODUCT_REPOSITORY`), stay on github.com and are refused for a product repository on an Enterprise site, so its token never goes to github.com; without a product repository their routes answer 404 before any provider request.

GitLab site URLs are deployment settings. OAuth state, credentials and account keys are bound to the configured site and OAuth application. GitLab API and OAuth calls reject redirects. Refresh-token rotation is serialized across hosted instances through Redis; local development serializes refresh in process. GitLab commits use per-file last_commit_id checks and preserve unrelated concurrent history.

## 4. Live editor

An edition may attach a live editor (`AppServices.liveNotes`): a framed external editor ([spec](../../specs/2026-11-15-live-notes/spec.md) §9) or the community's built-in editor ([spec](../../specs/2026-11-15-builtin-live-editor/spec.md) §9). The rules below hold for both kinds unless a bullet names one.

- **Frames:** each editor origin is deployment configuration, validated at start (`validateLiveEditorInfo`: a bare https origin, http only on loopback). The server drops adapter URLs on any other origin, and the web checks the origin again before framing. No page-wide CSP is added (a `frame-src` would break the third-party embeds notes use); the editor limits who may frame it. The app keeps `X-Frame-Options: DENY`, so `/live/open` is opened top-level.
- **Who may do what:** checking out, creating a live note, checking in, writing live and merging a text into a live note (`POST /api/live/merge`) need a signed-in person or a write grant whose credential may push to `main` (`canWrite`). Read-only grants read live text only. Signed-out requests make no adapter call and read Git text.
- **Author:** a check-in commit's author and co-authors come only from the edition's editor list, through `service.open`, never from a request; the person who asks for a manual check-in is named by their own sign-in, and only when their credential is the one that commits. A name or email `commitAuthor` refuses is skipped, never cleaned up. The edition must list in `detail.editors` only emails it has verified as the editor's own, as it must for `SignedIn.author` and `SignedIn.live`: an editor that lets people choose the email they edit under would let them author commits as anyone.
- **Check-in credential:** an adapter either commits with a credential of the deployment's own (0.20), or lists the `person` each editor signed in as and has `service.open` open the repository with that person's own credential. The engine then tries the editors in order and, in a manual check-in, the person who asked last; a refused one (`LiveCredentialError`, or the provider's 401, 403 or 404 on their own credential) is passed over and keeps their credit. The provider therefore enforces each person's access as the commit is made, no credential writes on behalf of someone who cannot, and when nobody's works nothing is committed and the text stays live. A person an adapter lists is checked (`realm` and `userId`), and a malformed one names nobody. `LiveCredentialError` names no credential detail, and neither does the `uncommittable` notice or its log line, which carry the link id.
- **Merging a text:** `POST /api/live/merge` takes `base` and `text` from the writer, who could write any text anyway; the base only decides how their own text lands, and the result is one more edit in their name. A conflict takes nothing. The answer kept for a repeat is keyed by the person, the link and the merge id together, so nobody answers, or forestalls, another person's merge by naming its id. `base` and `text` are held to the live text limit before anything is checked out.
- **Caches:** live texts are stored only under their own sha256 and checked against it when stored and when served; Git-keyed index and memo entries never hold live text, and memo keys include the live hashes. A request looks up only hashes its own `checkouts()` returned.
- **Tokens:** every field of a `v2.` revision is validated (repository ids, link ids, ASCII revisions of at most 256 characters, hex hashes), at most 32 live entries.
- **Routes:** `POST /api/live/sweep` compares the bearer with `MYGITNOTES_LIVE_SWEEP_SECRET` (at least 32 characters) over sha256 digests with `timingSafeEqual`, answers 404 without a secret and never logs it. `/live/open` redirects only to a same-origin note path built from validated parts, or to `/`, and reflects nothing from its query.
- **Errors:** an adapter failure that is not one of the live errors answers 502 `Live editor unavailable.` and names no adapter detail; a check-in logs a link's failure by id and reason, never with note text.
- **Limits:** live text up to 5 MiB, as other writes.
- **Drafts:** discarding, moving or renaming a pending note (`/api/live/discard`, `/api/live/retarget`) needs the rights of a check-in and the link's lease, commits nothing, and is refused for a note that has a Git path, so neither can remove or move a filed note. A draft someone typed content in is discarded only with `confirm: true`; an empty one (`isEmptyLiveDraft`) goes without it.

### Built-in live editor

- **Hosting:** `createApp` refuses a built-in editor on Vercel, without `APP_URL`, with an `APP_URL` that is not a bare `https` origin (`http` only on a loopback host), and with an adapter that has no `socketTicket`.
- **Socket origin:** `/live/socket` accepts only an `Origin` exactly equal to the `APP_URL` origin, checked before the upgrade; a missing or foreign `Origin` gets 403. This blocks cross-site WebSocket hijacking: another site's page can open a socket, but its `Origin` gives it away, and it cannot get a ticket either, since the ticket route sits behind the session and the HTTP Origin check. The HTTP check's fallback to the request's own host is not used for sockets: an upgrade behind a TLS-terminating proxy would read `http://` where the browser sends `https://`.
- **Socket credential:** the only credential is a ticket from `POST /api/live/socket-ticket`: 32 random bytes, single use, valid 60 s, stored only as its sha256, and bound to one person, one link and one epoch. It is issued only to a signed-in writer (`canWrite`) of a covered repository, for a note that is already live; read-only grants and signed-out requests get none and read the live text through the read overlay. Cookies on the upgrade are ignored, so a session alone opens nothing, and the socket is whoever its ticket names, whatever the tab claims.
- **Session end:** a ticket is checked against the session only when it is issued, so a socket does not outlive its session for long: the server closes every socket that was open `socketMs` (10 min by default, a `builtinLiveNotes` limit) with code 4000 (`Live ticket renewal`), on the next beat, and stores nothing a socket sends past that. The tab connects again silently and asks for a fresh ticket; once the person signed out or their session expired the ticket POST is refused, and the tab ends the session, offering any unsaved text to copy or download. Writes stop at most 60 s (a ticket's life) + `socketMs` + `beatMs` (15 s) after the session ended, about 11 min by default.
- **Identity:** editor names and emails come from the ticket (the identity's `live`, else its verified `author`, else the realm and user id), never from the client, and the ticket also records the person who signed in, whose own credential a check-in may commit with. The server overwrites every awareness state's `user` with that name and a colour derived from the person, and a connection can neither speak for nor remove another person's Yjs client id.
- **What a tab may store:** an update is refused before it is stored when it does not decode to its end, holds anything but text inserted into or deleted from the note's one text, names a client twice, or leaves structs waiting, so a tab cannot grow the stored state outside the text limit or leave a note that no process can load. `\r` and NUL a tab inserts are taken out by the server.
- **Epochs:** a reopened note is a new epoch; tickets, document loads and every append refuse another epoch, so text from an earlier checkout never enters a reopened note. A tab that was offline at the release is offered its own text to copy or download, and nothing of an earlier epoch's document is ever merged into a later one; a text can only come in as text, through `POST /api/live/merge`.
- **Limits:** messages up to 8 MiB, live text up to 5 MiB, queues before authentication up to 1 MiB and one document, 50 connections per document, 200 loaded documents per process, awareness states up to 4 KiB; text diffs for agent writes time out after 100 ms instead of blocking the event loop.
- **Store:** live text sits in Redis unencrypted, as the remote cache's live texts do, under keys namespaced by `MYGITNOTES_SESSION_NAMESPACE`. Live text carries no TTL, and the store refuses to start under a readable `allkeys-*` eviction policy, which could drop it.
- **Errors:** store and protocol failures answer `Live editor unavailable.` or close the socket with a reason; logs name link ids and reasons, never note text or tickets.
- **Self-hosted wiring (`MYGITNOTES_LIVE_EDITOR=builtin`):** the server holds no credential of its own for check-ins. Each is committed with the provider token the editor's own sign-in stored (the encrypted credential record their agent grants use, which has no TTL and outlives a sign-out, as it does for grants), looked up by the person's realm and user id (`IdentityService.personToken`); a person of another OAuth app or site names no credential. The start-up refuses the lightweight cookie mode, which stores none. `covers` takes only provider repositories of the deployment's own site, parsed from the id and rebuilt to compare, and people reach the adapter only through a repository their own token opened. The email a github.com editor is credited by is `<user id>+<login>@users.noreply.github.com`, built from the account the provider answered at sign-in, never a personal address and never a client's word; GitHub Enterprise and GitLab editors get no email. Live text and the tokens' records sit in the Redis that must not evict; `MYGITNOTES_CACHE_REDIS_URL` moves the remote cache, which holds copies of note texts under content hashes, to a Redis that may.
