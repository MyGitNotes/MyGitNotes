# Architecture

MyGitNotes is structured as a TypeScript monorepo using pnpm workspaces.

## Monorepo Layout

- `packages/core`: Core domain models, `.mygitnotes.yaml` (or the compatible `.github-notes.yaml`) schema & parsing, Markdown & YAML frontmatter parsing with exact round-trip preservation, resource classification, and path traversal guards.
- `packages/git`: Guarded Git service operations, Core update engine, and semantic commit message generation (with Gemini Flash-Lite and deterministic fallback).
- `packages/mcp-server`: Stdio Model Context Protocol (MCP) server providing safe note, asset, git, and workspace operations to coding agents.
- `apps/local-server`: Lightweight local HTTP bridge serving workspace APIs and static assets to the frontend web application.
- `apps/web`: Responsive, modern React frontend supporting List, Card, and Kanban views, pure Markdown & plain-text editors, asset manager, and crash-recovery drafts.
- `scripts/`: Cross-platform Node/TypeScript scripts for `bootstrap-workspace`, `update-core`, `migrate-workspace` and `convert-workspace`.

## Core Invariants

1. **Markdown is the source of truth**: Notes are plain Markdown files with optional YAML frontmatter. No proprietary database or HTML blob becomes authoritative over files on disk.
2. **Boundary between Core and User content**: `core` carries only product source and `main` carries only workspace content (`.mygitnotes.yaml`, notebook roots, assets, workspace Agent settings). The local server runs from a `core` worktree and edits the `main` worktree named by `MYGITNOTES_LOCAL_PATH`; `core` only fast-forwards and never merges into a content-only `main`. Fork-model workspaces whose `main` still carries the product merge Core with workspace Agent paths restored until they run `convert-workspace`.
3. **Round-trip fidelity**: Updating a note's frontmatter (e.g. changing Kanban column/status) preserves all unknown frontmatter fields and the original markdown text unchanged.

## Configurable sources

`mygitnotes.server.yaml` (or the compatible `github-notes.server.yaml`) selects a local repository, GitHub repository or GitLab project. Without a configured local path, a local source reads the application root only when it holds a workspace manifest (fork model); otherwise startup fails and names `bootstrap-workspace`. Local startup also rejects a workspace whose `schema_version` differs from `SUPPORTED_SCHEMA_VERSION` (now 3, compilations); `migrate-workspace` upgrades it, converting Screen lanes into `*.compilation.yml` files. Compilations are note-shaped files served through the note routes; there is no `/api/screen-page`. A compilation's items may name any notebook of its repository: `parseCompilation` takes the repository's notebook roots and checks only a dynamic folder source against them (local scans and the remote index pass every root; the remote index key carries them), `compilationRow` gives each item the notebook whose root holds its path, and the browser looks that notebook up only among the compilation's repository (`parseCompilationNote`), so a repository with the same root is never chosen. Product reference documents under `docs/agent/**` are served read-only from the application root, not from the workspace. Source configuration accepts `MYGITNOTES_*` and legacy `GITHUB_NOTES_*` environment variables.

A workspace is a list of member repositories on one site (`WorkspaceSettings`: `{ site, members, manifest }`; each `WorkspaceMember` has `ref`, `alias`, `default`, `hidden` and, in local mode, `localPath`). There is no home repository: each member's own `.mygitnotes.yaml` (manifest `schema_version: 4`) declares the notebooks it holds, and the default member is where the workspace opens. A deployment's member list comes from `deploymentConfigSource`: the repository the environment or the top-level `source:` names is the default member, and in local mode each worktree `repositories` in `mygitnotes.server.yaml` maps is another member, its alias derived from its repository's name in that order (the derivation phase 1 used, so keys and URLs do not change). Sign-in, `signedIn`, grants and Gists follow `settings.site`, which is known before any repository is reached; agent sessions, the default notebook and `/api/assets` without a notebook follow the default member. Every request resolves its configuration through the replaceable `WorkspaceConfigSource` and its repositories through `WorkspaceRepositories`, which opens each visible member with the signed-in credential (hosted) or its worktree (local), once per request, and reports unreachable ones as unavailable; a signed-out request whose private default repository refuses it fails as a whole, so the page asks to sign in. Revisions, drafts, commits, compilation/Focus/Study files, Agent files and Git status are per repository; one write never spans repositories. See [ADR 0001](../../adr/0001-multi-repository-notebooks.md).

Each repository's manifest is read and saved through `WorkspaceRepositories.manifestOf` / `saveManifest`, by repository id, from the store `settings.manifest(member, inRepository)` chooses (`localManifest` for a worktree, `RemoteManifest` for a provider repository, unless an edition keeps manifests elsewhere). It names the repository (`workspace.title`, else the repository name), says where it opens (`workspace.default_notebook`) and sets the `preferences` of its notebooks. A worktree without a manifest serves no notebook until one is saved (a local source creates it under `notes/`, a mapped repository at its root); a provider repository without one gets one derived from its top-level Markdown folders (`deriveWorkspaceConfig`, `manifest: 'derived'`). A manifest that does not load (YAML or validation error, unsupported schema, a notebook that still uses `source`, which schema 4 removed: `NotebookSourceError`, fixed by `pnpm convert-sources`) makes its repository unavailable (`invalid-manifest`) with the reason, while the other repositories keep working; the repository stays open for `saveManifest` (`handleOf`), so Settings can fix the file. `GET /api/workspace` reports `keyedConfig`, `defaultRepository`, `coreUpdate` and per repository `title`, `defaultNotebook`, `preferences`, `config`, `configRevision`, `manifestError` (with the file's text, or empty text when it cannot be read) and `unavailable`. A symbolic link is never taken for a manifest. `PUT /api/workspace/config` takes `{ repository, configYaml, configRevision }` and answers 409 when that repository's manifest moved: a remote revision is the branch head, a local one a hash of the manifest file (`MISSING_MANIFEST_REVISION` when there is none), checked under the worktree's mutation queue. Settings' manifest editor opens on the current notebook's repository (the default repository's without one) and keeps the person's unsaved text when only a revision moves; a 409 refreshes the workspace and keeps that text, so the next save goes against the current revision. The browser applies a note's repository preferences through `notebookPreferences(notebookId)`; the header shows the title of the shown notebook's repository, and the default repository's on Settings, Agents and all-notebooks pages (`pageRepository`). `files.hide_dotfiles` is obsolete: kept when a manifest sets it, never added. Hosted Core updates act on the deployment's product repository (`productRepository`: `MYGITNOTES_PRODUCT_REPOSITORY` or `product_repository`), not on a workspace repository; without one the `/api/core` routes answer 404 and `coreUpdate` is false, and naming one where each visitor chooses a repository fails at startup.

`RemoteSource` contains shared note, folder, asset, compilation and Study rules. `GitHubSource` and `GitLabSource` implement immutable reads and atomic commits. `createRemoteSource` selects the adapter for HTTP and remote MCP, and takes the author of the commits the source publishes when its token is a credential the deployment shares (`CommitAuthor`; GitLab `author_name`/`author_email`, GitHub the commit's `author`; without one the request is unchanged). `commitChanges` can name co-authors in `Co-authored-by` trailers. GitLab supports an HTTPS base URL and nested project namespaces.

OAuth follows the selected provider. Encrypted server records isolate site and account identity. GitLab refresh tokens are rotated under a credential lock and shared by browser sessions and persistent MCP grants. GitHub keeps its existing credential and grant identifiers; short-lived GitHub OAuth app tokens rotate under the same credential lock for persistent MCP grants, while GitHub browser sessions end with their access token.

See the [deployment guide](../../deploy.md).

### Themes

An edition adds palette families and picks the default one through `createWebApp(root, { themes: { families, defaultFamily } })`; both are optional, and the community edition passes none.

- `families` are `PaletteFamily` values (`id`, `name`, `license`, and `variants.light` and `variants.dark`, each a `PaletteVariant` of the colour roles the built-ins define; optionally `fixedMode`, a mode the family is always shown in, and `tokens`, custom properties set over the ones `index.css` derives). `PaletteFamily`, `PaletteVariant`, `PaletteMode` and the built-in `PALETTE_FAMILIES` are exported from `@mygitnotes/web`, so an edition can derive a family from a built-in.
- Registered families join the ten built-ins (nine colour families and E-ink), listed after them in the Settings theme picker and the editor's view panel. A registered `id` equal to a built-in's replaces that built-in in its place.
- `defaultFamily` names a built-in or registered family and is the family of a visitor with no saved choice; left out it is Flexoki. A name that matches no known family makes `createWebApp` throw before anything renders.
- A saved family id that is known (built-in or registered) is kept. An unknown or retired id resolves to the default family; the saved mode (light, dark or system) is kept either way.
- The registry is filled by `registerThemes` (`lib/themes.ts`) at the start of `createWebApp`, before the first render. Each call starts over from the built-ins, so `registerThemes({})` resets it, which tests rely on.
- E-ink (high contrast), family `eink` (`EINK_FAMILY` in `palettes.ts`, rules its tokens cannot reach in `src/eink.css`), is black on white for e-ink screens: muted, accent and status colours are black, lines and tints are black or white, shadows, blur and scrims are off, transitions and animations end at once, the root font is 18px, selected and pressed controls are outlined, and hover-revealed controls are always shown. It has one look (`fixedMode: 'light'`). CSS cannot detect an e-ink screen, so `createWebApp` asks the browser once for the device model (`detectEReader` in `lib/e-reader.ts`, `navigator.userAgentData.getHighEntropyValues(['model'])`, Chromium only, no `Accept-CH`) and `isEReaderModel` matches BOOX model names; the result is saved (`github_notes_e_reader`) for the next visit's first render. A detected e-reader shows E-ink only while the saved choice is the default family with `system` and the person has picked nothing in a picker (`github_notes_theme_chosen`, set by `setThemeChoice`); the saved choice itself stays as it was. `getThemeView()` (`useThemeView`) gives the choice, the family shown and `auto`; Settings → Preferences then says 「偵測到電子閱讀器，已使用電子紙主題」 and offers 「改用一般主題」, which records the default as chosen. Picking E-ink, or any family, in a picker always wins.
- `applyTheme` saves the resolved family id and the resolved colours (`github_notes_theme_tokens`) after resolution, which is what the inline script in `index.html` paints from, so a returning visitor's first paint already wears the registered family, and a visitor whose saved family is gone gets the new default's colours from the first visit on.

### Publication after other commits

A note is published after every commit of its text, not only after `/api/notes/commit` and `/api/notes` ([spec](../../specs/2026-11-16-sharing-public-collab/spec.md) S0). `commitPublisher` (`apps/local-server/src/publishing.ts`), built once in `createApp`, takes the note texts a commit wrote and does what those routes do after theirs: no Gist is pushed, since Gists sync only on the app's commit routes, and the edition's `PublishingService.syncCommitted`, when it has one, hears every note. Three commit paths call it:

- **A hosted `/mcp` write.** `openWorkspace` takes `committed`, which each remote reader it opens reports its commits to (`RemoteSource.onCommit`: the changes `commitChanges` wrote, so no text is read a second time, with the commit's `revision`). `/mcp` publishes them to the edition with the grant's person (`agentWrite`) and never pushes a Gist: the `gist:` id is caller-chosen text and would aim the person's token at any Gist they hold. A note that names one is logged as `[publishing] <repository id>/<path>: gist not updated by an agent write; updates on the next app commit`, and the owner's next commit of it in the app updates the Gist. A write to a checked-out note goes to the live editor and commits nothing, so it publishes at the note's check-in.
- **A tag commit** (`/api/tags/apply`), with the signed-in person. Tags are not in a Gist, so no Gist is pushed (`gistTextKept`).
- **A live check-in**, whoever started it (「立即簽回」, the sweep route, the schedule). `checkInLink` tells `LiveNotes.committed` of each commit right after `commitChanges` (`announceLiveCommit`: `{ repository, path, content, commit, source, author?, person? }`, `person` being whom `service.open` opened the repository as, so it is left out where the deployment's credential committed); `createApp` listens through `withLiveCommits`, which derives the adapter it hands to its routes, `/mcp` and the schedule without changing the edition's object, and still tells the adapter's own `committed`. A check-in commits with an editor's own credential where the adapter lists one ([Live editor](#live-editor), whose credential commits), else with the deployment's, and either way pushes no Gist: the text may be an agent's, typed through `/mcp` into the live note, and Gists sync only on the app's commit routes. A `gist:` note is logged as not updated, and the next commit of it in the app updates the Gist.

What it publishes (`committedNotes`): the changes with text that are notes of the repository's notebooks (`isNotebookContent`), so no agent file, `.templates/` file, compilation or excluded path, and nothing for a move, copy or deletion. `syncCommitted` gets `{ repository, notes, person?, revision? }`: `repository` is a `RemoteHandle` whose reader holds the credential that made the commit (the check-in's `service.open` source), `notes` are in the shape `sync` receives, `person` is the grant's, the signed-in one, or for a check-in the person whose own credential committed (none for the deployment's), and `revision` is the commit's, so a service can drop a publication a later commit of the note overtook (publications of one note may finish out of order; nothing orders them yet). The person's token is not handed to the service.

Nobody is shown the outcome. The commit's answer is byte-identical with or without publication, and the commit is never undone. The work goes to `AppServices.defer` where the deployment has one; without one, an `/mcp` call and a tag commit answer only after it settled (a serverless function may freeze once it has answered), and a check-in never waits. Failures are logged as `[publishing] <repository id>/<path>: <reason>`; what is thrown is logged by a fixed label only, never its name or message, since either may quote the note, and a `PublishSync.error` is logged as written, so a service must not quote the note in it. Without a service that has `syncCommitted`, nothing is called.

Not covered: the other routes that commit note text (the outline import, a Study review's status change) and the file manager's moves and copies; such a note is published at its next commit.

## Live editor

An edition may hand a remote repository's notes to a live (co-)editor ([spec](../../specs/2026-11-15-live-notes/spec.md)) through `AppServices.liveNotes`, a `LiveNotes` adapter (`packages/core/src/live-notes.ts`, its types and errors re-exported from `edition.ts`). Without one nothing changes. There are two kinds of editor. A framed editor (0.19) is an external editor the app frames; the community edition names none and holds only the contract and the checks on what an adapter returns. The built-in editor (0.20; [Built-in live editor](#built-in-live-editor)) is the community's own: notes are co-edited in the app's CodeMirror editor over Yjs, and an edition composes it with a credential of its own or the editors', while the community's own server turns it on from its environment ([Environment wiring](#built-in-live-editor)).

- `editor(repository)` names the editor of a covered repository, or null. `LiveEditorInfo` is a framed editor, `{ kind?: 'frame', origin, messageType, themeParam? }`, or the built-in one, `{ kind: 'builtin' }` (`isBuiltinEditor`). Every configuration it may answer is listed in `editors`, which may hold one builtin editor beside framed ones, so one adapter may cover some repositories with each kind. `createApp` throws at start when `liveNotes` is given with a local workspace, when `editors` is empty, or when one is invalid (`validateLiveEditorInfo`: a framed editor has a bare `https` origin, `http` only on a loopback host, no path or credentials, and `messageType` and `themeParam` of letters, digits, `_` and `-`; a builtin editor has no other key; any other `kind` throws; a framed value without `kind` is returned without one, so a 0.19 configuration round-trips byte for byte). With a builtin editor it also throws when `VERCEL` is set, when `APP_URL` is missing or not a bare `https` origin (`http` only on a loopback host), and when the adapter has no `socketTicket`. `liveEditorOf` refuses an answer that is not one of `editors`.
- `person(context)` holds the calls a signed-in person or a write grant makes (`checkouts`, `read`, `write`, `append`, `checkout`, `createPending`, `filed`, and the optional `merge` of [Merging a text into a live note](#merging-a-text-into-a-live-note); `read` of a pending note may also answer its `initialText`); `service` holds the check-in engine's calls (`repositories`, `checkouts`, `open`, `lease`, `detail`, `mergeIn`, `synced`, `release`, and the optional `discard` and `retarget` of [pending drafts](#pending-drafts-discard-move-and-rename)); `notify` hears of conflicts, deletions, notes that could not be filed and notes nobody's credential could commit (`uncommittable`), and the optional `committed` of each commit a check-in makes ([Publication after other commits](#publication-after-other-commits)). A `LiveContext` is `{ person, author?, live?, request }`: `live` (`LiveIdentity`, `{ name, email? }`, from `SignedIn.live` or a bearer grant's `live`) is how the live editor shows and credits the person, `author` when it is left out (`liveIdentityOf`); ordinary commits follow `author` alone. `socketTicket(context, repository, id)` is required beside a builtin editor and answers `{ ticket, document }`; `LiveRepository.socketTicket` checks the answer (`ticket` of 32–128 URL-safe characters, `document` `<link id>.<epoch>`, `liveSocketTicketOf`).
- An adapter maps its own failures onto `LiveStaleError` (409), `LiveLeasedError` (409), `LiveNotLiveError` (409), `LiveTooLargeError` (413) and, from `service.open` only, `LiveCredentialError` (403: the person it was asked to open the repository as cannot commit there); `liveAdapterError` turns anything else into `LiveUnavailableError` (502 `Live editor unavailable.`), which names no adapter detail. `CheckedOutError` (409, `code: 'checked-out'`, `paths`) is the refusal of a Git write that would touch a checked-out note.
- Texts are compared in normal form (`normalizeLiveText`: every `\r` and NUL removed) and identified by `liveContentHash`, the sha256 hex of its UTF-8 bytes; a CRLF note becomes LF at its first check-in.
- Every row an adapter returns is checked before use: `liveCheckoutOf` keeps only the contract's fields and drops, logging only the id, a row with an invalid id, a framed editor's row without its `editorUrl` and `embedUrl` or with one off the editor origin (a builtin editor's row carries no URL, and any it does carry is dropped), a path that is not a live-editable note of its notebook (`isLiveNotePath`: Markdown notebook content, no outline), or any other invalid field; `liveTextOf` checks a revision (printable ASCII, at most 256 characters) and that the hash is the text's own.
- A pending note (created in the editor, not yet filed) has the virtual path `<notebook root>/.live/<id>.md` (`livePendingPath`, `parseLivePendingPath`); a dot folder is never notebook content, so it cannot collide with a Git note.

`@mygitnotes/local-server/testing/live-notes-contract` (`liveNotesContract(name, makeFixture)`) is the behavior every adapter must keep; the fixture gives the adapter, a covered repository, a notebook key and its root, `person(n)`, and the editor's hooks `type`, `setActive` and `advance`. Its credential cases run for an adapter that lists its editors' `person` (required with the fixture's `ownCredentials: true`) and its merge cases for one with `merge` (required with `merges: true`); an adapter with neither is passed over by both, as a 0.20 adapter is. The memory adapter takes `persons: true` and `merge: true` to be either. `…/testing/memory-live-notes` (`memoryLiveNotes`, with `memoryLiveClock`) is the in-memory reference that passes it: revisions are `e<epoch>:<n>` while a session is open and `h:<hash>` otherwise, a write on an older revision of the open session is rebased over the typing since, and its `service.open` returns a `MemoryEditionSource` over the same files that commits as the given author. Memory sources over the same files share one commit counter and log (`memoryCommits`), so the person side and the service agree on heads, a file's history and past blobs read back, and a commit on a head that moved is refused with `StaleRevisionError`, as a provider refuses it.

Reads and writes (spec §2–§4): `openWorkspace(…, { liveNotes })` (`requestWorkspace` and `/mcp` pass it) hands a remote reader opened for a signed-in person, or a grant's person, a `LiveRepository` view (`liveRepository`, `packages/core/src/live-repository.ts`) when `liveEditorOf` names an editor for its repository; a signed-out request gets none and makes no adapter call. The view asks the adapter's person calls for the repository's links once per request, checks each row, and resolves its notebook key against the repository's alias. Through `RemoteSource.useLive`, `readFile` and `note()` answer a checked-out note's, or a pending note's virtual path's, live text (`note()` fresh, with `live: LiveNoteState`), `notePaths`, `notes()` and the catalog index list pending notes, and the index lays the live title, metadata, tags, status and size over the Git index, which is itself built from Git blobs only (`readSnapshotFile`), so no cache keyed by a Git id holds live text. Bulk reads take live texts from the shared cache under `mgn:live:v1:<repository>:<sha256>`, checked against the hash both ways, and on a miss read the adapter once per link and listed hash per process (never sharing one link's read with another of equal text). Memo keys add a hash of the live links' `[id, path, contentHash]` of their notebooks. `commitChanges`, `save` and `commitNotes` refuse with `CheckedOutError` any change that touches a checked-out or pending path, after the write-access check and before the stale check; a change that touches no `.md`/`.markdown` path asks the adapter nothing, so configuration, folder metadata, documents, skills and assets still commit while the editor is down; the note shell refuses `cp`/`mv` of a checked-out source too. A single-note text write on the internal revision `live:<id>:<contentHash>:<liveRevision>` (`liveBase`, never shown; the hosted router builds it from a `v2.` token's entry, and `POST /api/notes` treats one as no revision) goes to `RemoteSource.writeLive`, and `append` on a checked-out note to `appendLive`; both need `canWrite`. JSON error answers add `code` and `paths` for `CheckedOutError` (`checkedOutFields`).

Check-in (spec §5–§7): `checkInLink(liveNotes, repository, id, { mode })` (`packages/core/src/live-checkin.ts`) leases the link, reads its `detail`, opens the repository with `service.open(repository, author)` (whose source never gets a live view, so the check-in is never refused as checked out) and commits with `commitChanges`. With the deployment's own credential (an adapter whose editors list no person; the next paragraph covers the editors' own), the author is the earliest person among the editors since the last sync that `commitAuthor` accepts, else the earliest agent, else none; the other accepted editors are `Co-authored-by`, and refused ones are skipped and listed in `skippedEditors`. The message is `docs(notes): live edit <name>` (`file live note` for a first filing) with the trailers `Live-Link`, `Live-Content: sha256:<hash>`, `Live-Overwrote` on a conflict and `Agent-Edit` when an agent edited. When Git already holds the live text it only acknowledges (`synced` without a commit), which also covers a commit whose acknowledgement was lost; on an unmoved head, or when the newest commit touching the note is this link's own check-in (`Live-Link` and a `Live-Content` of Git's text: a lost acknowledgement followed by typing), it commits the live text; when Git moved, `mergeLiveText` (`live-merge.ts`, a diff3 line merge over the whole file on Myers' O(ND) line diffs from `live-text.ts`, where hunks of the two sides that overlap or touch conflict unless both made the same change; a few changed lines of a 233 KiB note merge in milliseconds) merges Git's changes into the live note with `mergeIn` before committing (the base read up to the editor's 5 MiB), reading the detail again for the text it commits and naming the editors of both reads, so someone who typed in between is credited, and on a conflict, or a note deleted in Git, the live text wins, the commit names what it overwrote and `notify` hears of it. A pending note is filed by `fileLivePath` (`title` from the note, `date`/`time` from its frontmatter or `since` in `MYGITNOTES_TIMEZONE`, other names from its frontmatter, `-2` … `-99` on a taken path); a missing value, or a path over 1024 bytes or with a part over 200, leaves it pending with an `unfiled` notice. Before filing, the rule's paths are searched for an earlier filing whose acknowledgement was lost, recognized only by its newest commit being this link's check-in (another note that merely holds the same text is not it): one holding the live text is only acknowledged, and one with typing since takes it. Known limit: when such an acknowledgement is lost and the rule then renders a different path (the title changed, or a taken path was freed), the note is filed a second time; no text is lost, and the earlier file stays in Git. A provider `StaleRevisionError` retries once within the lease; nothing is committed after a 4-minute deadline. `release` refused as `active` is retried three times 2 s apart by hand and left for the next tick when scheduled. `sweepLive` checks in the links whose `since` is before the instant, two at a time, at most 500, logging failures by id. `LiveRepository.checkIn(path)` is the manual check-in, reached through `RemoteSource.checkInLive`, which needs `canWrite`.

Whose credential commits ([collab-first spec](../../specs/2026-11-16-collab-first-self-host/spec.md) A6). An adapter may list on each editor the `person` (`{ realm, userId }`) they signed in as; `checkInLink` then commits with the editors' own credentials. Its candidates (`liveCommitters`) are the editors with a person, people before agents and each group by who typed first, a person once however many of their entries typed; then, in a manual check-in, the person who asked for it (`LiveCheckInOptions.requester`, which `LiveRepository.checkIn` sets from its context), unless they are an editor. It calls `service.open(repository, author, { person })` for the first candidate: the author is that candidate (their accepted name and email, or none, and then the commit is authored by the account of their credential), and every other accepted editor is a `Co-authored-by` (`liveAuthorship(editors, committer)`). A `LiveCredentialError` from `open`, or for a person's own credential a provider 401, 403 or 404 while reading or committing, sends the next attempt on to the next candidate, reading everything again; a refused candidate keeps their credit as a co-author. With no candidate left nothing is committed: the result is `reason: 'uncommittable'`, `notify` hears `uncommittable`, the lease is given back (`unlease`), and the next check-in tries everyone again. Where no editor lists a person (a 0.20 adapter), there is one candidate, the deployment's own credential, opened as `service.open(repository, author)` exactly as before; any other failure is thrown as before. MCP `check_in_note` lists `uncommittable` among its reasons in the tool variant of an adapter that discards drafts, and the 0.19 variant is unchanged.

A check-in needs nobody's credential for what commits nothing. A pending note to discard is decided before `open`. A note whose live text is still the text of its base (`contentHash === base.contentHash`: only viewed, or typed in and typed back) runs the 0.20 path when a candidate credential opens the repository, so Git's newer text merges into it and a note deleted in Git is written back, keeping the nightly behavior of existing adapters byte-identical; only when no candidate can open (the `uncommittable` branch) is it acknowledged with its base as the receipt and released, since the live note holds nothing Git lacks. `liveRowBase` reads the row for that without the repository's notebooks.

The idle check-in (A5): `sweepIdleLive(liveNotes, { now, idleMs })` checks in, as a scheduled sweep does (two at a time, at most 500, `discardUntyped`), every link whose `activeEditors` is 0 and whose `lastEditAt`, or `since` when nobody typed, is at least `idleMs` (5 min) ago. The adapter's own idle rule decides who is active: in the built-in editor a closed tab leaves at once and an open one stops counting 10 min after its last activity. A release refused as `active` is left for the next tick.

The routes (`apps/local-server/src/live-routes.ts`, mounted only with `liveNotes`): `POST /api/live/checkout`, `/api/live/new` (a template rendered as `/api/templates/render` does, with its path rule from `livePathRule`; without one `<folder>/{{title}}.md`, and a note without a title of its own takes the one given) and `/api/live/checkin`, each for a signed-in writer (`canWrite`) of a covered repository (a checkout of a pending note's virtual path answers its own link, `outcome: 'joined'`, until it is filed); a repository without an editor, an outline or a template file answers 400 `code: 'not-live'`, an editor refusing the size 413 `code: 'too-large'`. `POST /api/live/sweep` is mounted before the workspace routes and answers 404 without `MYGITNOTES_LIVE_SWEEP_SECRET`. `GET /live/open` (with `requestWorkspace` on `/live`) redirects to `noteWebPath` or `/`. `GET /api/workspace` adds `live` per repository (the editor, or null), from configuration alone, and `/api/notes/read` of a released pending path answers 404 `{ movedTo }`. `POST /api/live/merge` is described under [Merging a text into a live note](#merging-a-text-into-a-live-note). The in-process schedule (`live-schedule.ts`) starts in `createApp` with `liveNotes` outside Vercel, reading `MYGITNOTES_LIVE_CHECKIN_AT` and `MYGITNOTES_LIVE_IDLE_CHECKIN` at start: beside the nightly ticks, an idle tick falls every 60 s (jittered by up to 10 s either way) and runs `sweepIdleLive`, with a turn of its own, so a long nightly sweep holds no idle tick off. `MYGITNOTES_LIVE_IDLE_CHECKIN` is `5m` by default, `1m` to `60m`, or `off`; any other value stops `createApp` (`liveIdleSetting`), as a bad `MYGITNOTES_LIVE_CHECKIN_AT` does. With the nightly check-in `off` the idle tick still runs. An edition with a framed adapter gets the idle tick on upgrade (`MYGITNOTES_LIVE_IDLE_CHECKIN=off` opts out). A link the idle sweep leaves `uncommittable` or `unfiled`, or whose check-in throws, waits before its next idle try (`LiveIdleBackoff`: 1 min doubling to 30 min, keyed by link id with its `contentHash` and `lastEditAt`, reset when either changes; a `leased` answer keeps it), and its notice goes out once per that key; the nightly sweep and 「立即簽回」 ignore it. While the editor's link list fails, a signed-in read of a Markdown note of that repository answers 502 `Live editor unavailable.`; the workspace, folders and signed-out reads still answer.

The web app (spec §8): `GET /api/workspace` names each repository's editor in `live`. For a writer of such a repository, `editorProps` hands every Markdown note that is no outline, compilation or template file a `live` (`LiveNoteEditing`, `apps/web/src/lib/live-api.ts`), and `NoteEditor` opens it read-only with 編輯 (`useLiveEdit`, `components/live/`): in zoom 編輯 calls `/api/live/checkout` and swaps the body for `LiveEditorFrame`; a Focus pane, graph card or compilation section opens zoom instead, which checks out on arrival (`requestLiveEdit`); a pending note frames at once; a note address with `edit` (bare or with any value: `<note>?edit`, `<note>?zoom&edit`, what an app that created the note with MCP `save_note` links to) does what 編輯 does once the note's editor shows it (`liveEditLinkTarget` and `LiveEditLinkProvider`, `app/live-edit-link.tsx`; `lib/live-edit-url.ts`): zoom checks it out, and the Focus's active pane, a phone's included, opens zoom once the Focus settled on the note and marked the address as its own; the first editor of the routed note in zoom or a pane claims it, once per history entry, and `edit` leaves the address with a replace that keeps every other part of the query as written, the hash and the entry's state (only on the entry the page still shows, `useCurrentEntry`), so a reload or Back does not check out again. An editor with no `live` (a reader, a signed-out visitor, a deployment without a live editor, an outline or template) never claims it, so the address keeps `edit` and the note reads as usual; `noteReturnRoute`, `handleOpenNote` (its query, `returnTo` and trail) and the folder index drop `edit`, so no other note inherits it. `edit` is not the list filter `live=` and leaves `mode=` alone (`?edit&mode=split` checks out; the live editor has one mode); a `too-large` or `not-live` refusal gives the direct editor back. `LiveEditorFrame` frames the embed URL (with `themeParam`) only when its origin is the editor's, with no `sandbox` or `allow`; `liveStatusOf` (`lib/live-message.ts`) accepts a status message only from that origin and the frame's own window, of the editor's `messageType`, with `users` an integer 0–10000 and `saved`, `connected` and `released` booleans (`released` may be left out); a theme change is posted as `<messageType>:theme` to the editor origin. 「立即簽回」 unmounts the frame before `POST /api/live/checkin` and reports a note that stays open; a check-in refreshes the workspace, the zoom that reloads says 「已簽回」 once (`markCheckedIn`), and a pending note is followed to where it was filed, as does a route to a virtual path that `/api/notes/read` answers with `movedTo`. Rows, cards, Kanban cards, the Focus list, the hover card and the phone note bar show `LiveBadge` (「編輯中 · N 人」, 「編輯中」, 「未歸檔」) and lock status, drag, move, rename, delete and bulk actions with 「編輯中，請先簽回」; `responseError` turns any 409 `code: 'checked-out'` into the same text with its paths (the file manager, asset moves and restore included), and the web agent tools refuse a checked-out note, read afresh since a checkout moves no revision. A new note of a live repository is created pending through `/api/live/new`, after `LiveNewNoteDialog` asks for the template path's placeholders other than `title`, `date` and `time`. The history labels a `Live-Overwrote` commit 「覆寫了 <sha>」, linked to that commit when the history lists it. Note queries of a live repository refetch on window focus and every 60 s (`liveRefresh`). Where the workspace has a live repository, the sidebar's status section (and the phone filter sheet) adds 「即時編輯」 with 編輯中 and 未歸檔, either or both, kept in the `live` URL query (`?live=editing&live=pending`) and sent as `NoteQuery.live`; without a live repository the web ignores `?live=`. The search takes `is:live` (any live note) and `is:pending` (未歸檔 only) in every workspace, also one without a live editor and for signed-out readers, where they match no note; `noteSearchTerms` takes them out of the free text before matching, leaving the text between them as typed, each stretch matched on its own (a token never joins its neighbours into a phrase), and each token shows as its own filter chip. The web list, Focus search, link completion and the compilation title picker therefore cannot search those literal words, and there is no escape; MCP `search_notes` and `list_notes` still treat them as text. Note query cursors are not live-aware: a checkout or a new pending note between two pages can shift rows, and cursors issued before the deploy that added `NoteQuery.live` get one 400 and restart the list. Live state is read from the editor, never written to frontmatter. `scripts/dev-live-memory.ts` (`apps/local-server/dev/live-memory.ts`, not built or shipped) runs the app over memory sources with the memory adapter and a stub editor on a second loopback port; `pnpm --filter @mygitnotes/local-server typecheck:dev` type-checks it.

### Pending drafts: discard, move and rename

Two optional service calls act on a pending note (no path) without a commit ([spec](../../specs/2026-11-15-builtin-live-editor/spec.md) §19–§20). `discard(repository, id, lease, { contentHash })` drops the note and its live text; it is refused like `release` (`active`, `changed`), and afterwards the link is gone, so `filed` answers nothing for it. `retarget(repository, id, lease, { pathRule })` sets the rule its first check-in files it by and answers the row with that `pathRule`; the text is untouched, so open editors do not hold it, a link with a path is refused with `LiveNotLiveError`, and the lease ends with the call either way, so a move never holds a check-in off. An adapter without them keeps 0.19's behavior, and the web keeps delete, move and rename of a pending note disabled. `/api/workspace` adds `discard: true` and `retarget: true` to a repository's `live` only where the adapter has the call, so the answer for an adapter without them stays byte-identical. Reads carry `LiveNoteState.pathRule` for a pending note only where the adapter can retarget (`liveNoteState`).

- `POST /api/live/discard { notebookId, path, confirm? }` (a pending virtual path, the rights of a check-in; `discardLink` in `live-checkin.ts`) takes the lease and reads `detail`. A draft that has editors and is not empty needs `confirm: true`, else 409 `code: 'has-edits'`; a release refused as `active` is retried 3 × 2 s as a manual check-in is. It answers `{ discarded: true }` or `{ discarded: false, reason }`, and 400 `not-live` for a filed note or an adapter without `discard`.
- `POST /api/live/retarget { notebookId, path, folder?, name? }`: core builds the new rule from the old one (`retargetLivePathRule`): `folder` replaces its folder and keeps the name pattern, so `{{title}}` still names the file; `name` fixes the file name. A name with a `{{placeholder}}`, an outline or template file name, or one too long to take `-99` is refused (400), and `.markdown` is kept. While a check-in holds the lease the call is asked again 3 × 2 s, then answers 409 `code: 'leased'`. It answers `{ checkout, destination: { folder, name } }` (`livePathRuleParts`). A destination taken at filing time still gets `-2` … `-99`.
- **Empty drafts** (§19.1): `isEmptyLiveDraft(text, initialText?)` judges the body after the frontmatter. It takes out, whole and trimmed and each once, the lines of the text the link was created with (`LiveDetail.initialText`), or without one the web's default new-note lines (`LIVE_DEFAULT_DRAFT_LINES`, `@mygitnotes/core/live-default-draft`: `# Untitled`, `Write your note here.`, `# 未命名`, `在這裡寫下筆記。`). The draft is empty when what is left holds no letter, digit, image or embed (`![`, `<img`, `<iframe`, `<video`): whitespace, punctuation, Markdown markers and emoji alone are empty, while one CJK character, a digit, a changed heading or a default line written a second time is content. `apps/web/src/lib/new-note-default-draft.test.ts` fails when a shipped locale's default heading or body is missing from the list.
- **Check-in of a draft:** where the adapter has `discard`, a check-in (「立即簽回」 or the sweep) discards an empty draft instead of filing it, whoever typed in it, and answers `discarded: true, reason: 'empty'`; the sweep also discards a draft nobody typed in (`untyped`). A draft with content is filed as in 0.19, and a filed note is never discarded. The built-in and memory adapters keep the text `/api/live/new` created the link with as its initial text, so a draft left as it was created (a template's untouched body, or the default heading and placeholder line) is discarded by 「立即簽回」 and by the sweep and never committed. MCP `check_in_note` reports it as `discarded` (see [MCP](../mcp/index.md#notes-being-edited-live-編輯中)).
- **Web:** a pending note's bar shows 「捨棄草稿」 where the repository's `live` has `discard`, and every delete entry (row, card, Kanban card, note menu, phone) on a pending note calls the discard route: an untyped or empty draft goes at once (「草稿是空的，已捨棄」), a typed one after 「捨棄這份草稿？內容不會存進 Git。」. Where it has `retarget`, the move dialog and rename call the retarget route, multi-select moves retarget each pending note and commit the rest, and the row and the 未歸檔 badge show 「歸檔到：<folder>/<name>」. The frame or collaborative editor closes first, as for 「立即簽回」.

### Merging a text into a live note

The optional person call `merge(repository, id, { base, text, mergeId })` ([collab-first spec](../../specs/2026-11-16-collab-first-self-host/spec.md) A4) takes a text written off the live note into it: a draft made offline on the text Git held, or what a tab typed after its note was released. It is a three-way merge over what the note became since `base`, lists the person among the note's editors, and answers `{ applied: true, contentHash }` or `{ conflict: true }`, which takes nothing. The writer names the base: it only decides how their own text lands, and a writer could write any text anyway. A repeat of the same `mergeId` (`isLiveMergeId`: 8 to 128 letters, digits, `_` or `-`) by the same person for the same link answers what the first answered, for a day, also after the note was released and reopened, and takes nothing twice. `LiveRepository.merges` says whether the adapter has the call, and `LiveRepository.merge` checks the id and the answer (`liveMergeAnswerOf`). Typing a built-in editor tab kept also names `typedIn: { document, update }`: the ended epoch's document (`<link id>.<epoch>`) and the tab's whole Yjs update of it. The built-in adapter then merges on the text that document ended with (`LiveStore.ended`, kept a day after the release) and the update applied to it, so typing the server stored before the tab heard so (an acknowledgement lost with the socket, or the session's first one) lands once. Where that document holds changes the tab never had (someone else typed while it was cut off), the tab's text is merged by character instead, on what both documents had (the units both know that not both deleted), with `uncertainBase`, so two people who replaced one line conflict as A3.1 asks rather than Yjs stringing both together (`typedInTexts`); once that document is gone it merges on `base` with `rebaseLiveText`'s `uncertainBase`, where two different insertions at one point conflict instead of both landing.

`POST /api/live/merge { notebookId, path, base, text, mergeId, typedIn? }` (`typedIn.update` in base64) has the rights of a checkout (a signed-in writer of a covered repository, `canWrite`), and makes that checkout first when the note is not live (`checkOut` in `live-routes.ts`, shared with `/api/live/checkout`; a pending note's virtual path answers the link it is). It answers `{ applied: true, contentHash, checkout, outcome }`, or 409 `code: 'merge-conflict'` with the `checkout`. An adapter without `merge` answers 400 `code: 'not-live'` and checks nothing out; `base` or `text` over 5 MiB answers 413 `code: 'too-large'`; a body is at most 8 MiB as every JSON body. `/api/workspace` adds `merge: true` to a repository's `live` only where the adapter has the call. Nothing is committed by a merge: the text is live, and a check-in commits it. The web calls the route to hand text over between the browser and the live note ([Collab-first and offline handover](#collab-first-and-offline-handover-web)).

### Built-in live editor

`builtinLiveNotes(options)` ([spec](../../specs/2026-11-15-builtin-live-editor/spec.md) §2–§7; `apps/local-server/src/live-builtin/`, exported from `edition.ts` with `redisLiveStore`, `memoryLiveStore`, `liveStorePrefix` and the store types) is a second `LiveNotes`. Its notes are Yjs documents kept in a live store and typed into over a WebSocket on the app's own server. Options: `covers(repository)`, `open(repository, author?, as?)` (the repository a check-in commits through, its commits authored by `author`; `as.person` is the editor the engine commits as, whose own credential an edition may open it with, throwing `LiveCredentialError` when they cannot commit there; the check-in engine is its only caller), `store`, and optionally `notify`, `appUrl` (default `APP_URL`), `clock` (tests) and `limits`. It answers `editors: [{ kind: 'builtin' }]`, person calls with `merge`, `service` with `discard` and `retarget`, `socketTicket`, and three members of its own:

- `started` resolves once `store.check()` passed and rejects with the store's refusal. It has no handler, so a composition that does not await it is stopped by the unhandled rejection (fail fast, since the factory is synchronous); every call waits on it and fails with `Live editor unavailable.` after a refusal.
- `upgrade(request, socket, head)` takes a request whose target up to its `?` is exactly `/live/socket` and returns true; any other target returns false and is the caller's. After `shutdown()` began it answers 503. The `Origin` must equal the app origin (`appUrl`, else `APP_URL` read as each socket opens) exactly; a missing or foreign one gets 403, and an origin that is not `http(s)` refuses every socket. Cookies on the upgrade are ignored: the socket ticket is the only credential.
- `shutdown()` refuses new upgrades and authentications (`unavailable`); spends up to 80 % of `shutdownMs` (15 s) on pending messages, server writes and compactions; then closes every socket with 1012 (cut off after 2 s), so tabs reconnect to whichever process serves next; then writes the presence of those who left and compacts once more. A timeout logs the documents it did not compact; their acknowledged updates are in the log anyway. A second call returns the first.

**Environment wiring** ([collab-first spec](../../specs/2026-11-16-collab-first-self-host/spec.md) A8, A6). `apps/local-server/src/index.ts` (what the Docker image runs) only calls `startServer()` (`server.ts`), which asks `environmentLive(base, configSource)` (`live-env.ts`) for the editor the environment turned on. With `MYGITNOTES_LIVE_EDITOR` unset or `off` it answers nothing, and the server is composed exactly as before: `createApp(base, { configSource, piAgent })`, no upgrade handler for a remote deployment, no signal handler.

| Variable | Meaning |
| --- | --- |
| `MYGITNOTES_LIVE_EDITOR` | `builtin` turns the editor on; unset, empty or `off` leaves it off. Any other value stops the server (`liveEditorSetting`). |
| `MYGITNOTES_LIVE_REDIS_URL` | The live store's native Redis (`redis://` or `rediss://`); `REDIS_URL` when unset. A Redis reached over REST is refused. |
| `MYGITNOTES_CACHE_REDIS_URL` | For every remote deployment, with or without the editor: the remote cache's own native Redis (`remote-cache-store.ts`), so cached reads never fill a Redis that must not evict. `REDIS_URL` when unset, as before. |
| `MYGITNOTES_LIVE_IDLE_CHECKIN`, `MYGITNOTES_LIVE_CHECKIN_AT`, `MYGITNOTES_TIMEZONE`, `MYGITNOTES_LIVE_SWEEP_SECRET` | The check-ins, as [above](#live-editor). |

With `builtin`, `environmentLive` throws, naming what to change, for a local source, for sign-ins kept in cookies (`storageMode() === 'cookie'`: no stored credential exists), without a native Redis for the live store, on Vercel, and for an `APP_URL` that is not the app's bare origin (`checkBuiltinLiveHost`, which `createApp` asks again). Otherwise it builds the record store, the stored sessions, the workspace choices and the remote cache `createApp` would build by itself, the default identity with `{ live: true }`, and `builtinLiveNotes` over `redisLiveStore`:

- `covers(repository)`: every provider repository on the deployment's site (`providerSourceOf(site, id)`, which rebuilds the id from the parts it read), so GitHub, GitHub Enterprise and GitLab repositories, never an edition's. Rights stay per request: a person reaches the adapter only through a repository their own token opened, and checkouts, tickets and merges need `canWrite`.
- `open` (`liveOpen`): the repository with the token `identity.personToken(as.person, site)` answers, through `openRemoteRepository`. Nobody to commit as, a repository that is not the site's, no stored token, and a `CredentialRejected` are a `LiveCredentialError`. There is no deployment credential: a note whose editors were recorded without a person can only be committed by someone asking for its check-in.
- `IdentityService.personToken?(person, site)` is the person's own provider token with no request at hand. The default identity answers the credential record their sign-in stored (`credentialToken(store, credentialId(userId, provider), site)`, refreshed under the credential lock as an agent grant's is), and nothing for another realm or a cookie session.
- Names (`providerIdentity(services, { live: true })`, `providerLiveIdentity`): on github.com `SignedIn.live` is `{ name: login, email: '<user id>+<login>@users.noreply.github.com' }`, the noreply address GitHub documents for an account; on GitHub Enterprise and GitLab it is `{ name: login }`, so such a person is shown, authors a check-in through their own token and is nobody's co-author. An agent grant's edits carry the grant's person and no name, so an agent that edited alone has the check-in authored by the account of that person's token.

`startServer` awaits `live.started` before it listens, hands each upgrade to the editor first and then to the local agent panel (a socket nobody takes is destroyed), and on `SIGTERM` runs `live.shutdown()` and then closes the server and its open connections; `RunningServer.close()` does the same for a test. `compose.yaml` holds a commented `cache` Redis for `MYGITNOTES_CACHE_REDIS_URL`, and `docker.env.example` the variables. `docs/deploy.md` ("Optional: the built-in live editor") is the self-host's guide: the variables and refusals, the two Redis instances (the live one `noeviction` with an append-only file, the cache's `allkeys-lru`), WebSockets through the reverse proxy, and Caddy behind Cloudflare passing `CF-Connecting-IP` on as `X-Forwarded-For`.

An edition composes the editor on its own server (the comment in `live-builtin/index.ts`):

```ts
const live = builtinLiveNotes({ covers, open, store: redisLiveStore({ url: process.env.REDIS_URL! }) });
const app = createApp(base, { …, liveNotes: live });
const server = app.listen(port, host);
server.on('upgrade', (req, socket, head) => { if (!live.upgrade(req, socket, head)) socket.destroy(); });
process.once('SIGTERM', async () => { await live.shutdown(); server.close(); });
```

A server that already handles upgrades (the local agent panel) asks each handler in turn.

**Store** (`store.ts`, `redis-store.ts`, `memory-store.ts`). The adapter never sends raw commands: every compound step is one atomic `LiveStore` call (`checkout`, `createPending`, `append`, `compact`, `lease`, `leaseHeld`, `leaseRead`, `synced`, `release`, `discard`, `retarget`, `presence`, `activePeople`, `putTicket`, `takeTicket`, …), and every time is the adapter's clock, passed in, so the kit's `advance` works against Redis too. `redisLiveStore({ url, prefix? })` takes a native `redis://` or `rediss://` URL and keeps its own connection with 10 s connect and command timeouts; a failed command throws `LiveUnavailableError`. Each compound call is one `EVAL` script that uses nothing newer than Redis 2.6 and builds some key names itself, so the store needs a single Redis, not a cluster. Keys sit under `P` = `liveStorePrefix()` = `<recordKeyPrefix()>:live-store:v1`, namespaced by `MYGITNOTES_SESSION_NAMESPACE` as sessions are and apart from the remote cache's `…:cache:mgn:live:v1:` text keys; `rk` and `pk` are the first 32 hex of the sha256 of the repository id and of the path:

| Key | Type | TTL | Holds |
| --- | --- | --- | --- |
| `P:repos` | set | none | repositories with live links |
| `P:r:<rk>:links` | set | none | the repository's live link ids |
| `P:r:<rk>:path:<pk>` | string | none | the link id of a path, kept after a release |
| `P:link:<id>` | hash | none | the link (`epoch`, `seq`, `gen`, `contentHash`, `contentSeq`, …; `base` and `conflict` as JSON) |
| `P:doc:<id>:<epoch>` | string | none | the epoch's compacted Yjs state, base64 |
| `P:doc:<id>:<epoch>:log` | list | none | Yjs updates since the last compaction, base64 |
| `P:editors:<id>` | hash | none | editor key to `StoredEditor` JSON |
| `P:initial:<id>` | string | none | the text a pending link was created with |
| `P:lease:<id>` | string | lease + 60 s | `{ token, until, readSeq, readHash }` |
| `P:presence:<id>` | hash | 90 s, refreshed | process id to its people's last activity |
| `P:ticket:<sha256>` | string | 60 s | a socket ticket, kept under its hash |
| `P:tickets:<id>` | set | 60 s, refreshed | the link's ticket hashes, deleted with it |
| `P:merge:<sha256>` | string | 24 h | `{ answer, until }`: what a merge answered, under the sha256 of who merged, into which link, under which merge id |
| `P:ended:<id>:<epoch>` | hash | 24 h | a released epoch's document (`state`, `log` base64 comma-joined, `until`), the base of a merge of typing a tab kept of it |

Live text and link records carry no TTL, so a `volatile-*` eviction policy never takes them. The TTLs that exist are a backstop in real time; what a lease, a presence entry or a ticket is worth is decided by the time the caller passes. A released link keeps its record and path mapping, so `filed` answers and a reopen reuses the id; a release deletes the epoch's editors, presence and tickets and moves its document and log to `P:ended:<id>:<epoch>` for a day (`ended(id, epoch, now)`; a `volatile-*` policy may take it early, and a merge then conflicts rather than doubling text), and a discard deletes those, the link record and the initial text (filing a pending note drops its initial text too). A `StoredEditor` holds the `person` its first append named, and one recorded by 0.20 holds none. A merge's answer is written by the same `append` script that appends its update (`append(…, merge?)`: when the key already holds an answer that still counts at the time passed, nothing is appended and `{ merged }` gives it back), is read by `mergeAnswer(key, now)`, and outlives the release of its link, so a repeat in the reopened note finds it. **Eviction check:** `check()` reads `INFO memory`, which managed services allow where they refuse `CONFIG`. A readable `allkeys-*` `maxmemory_policy` throws ("Redis may evict any key …"), so the deployment does not start; `noeviction` and `volatile-*` pass; an unreadable policy warns and starts. `INFO persistence` with `aof_enabled:0` and no RDB save in the last hour warns that a Redis restart loses typing since the last check-in. Under `noeviction` a full Redis refuses the append, so the tab shows 未儲存 rather than losing text silently. `memoryLiveStore()` makes the same calls over `Map`s with the same atomicity, for tests, the dev composition and a deployment that accepts losing live text on restart; two adapters may share one, which is how the two-process tests run without Redis.

**Documents** (`documents.ts`): one Hocuspocus 4.8 instance per adapter, used as a library (no listener); a document is named `<link id>.<epoch>` and holds one `Y.Text` named `content` in normal form.

- *Seeding:* `checkout` (created or reopened) and `createPending` seed the epoch's state in the same atomic call that creates the link or opens the epoch, and never when a document loads. A live epoch whose state is missing is refused and logged by id as data loss, never reseeded, because a reseed duplicates the text of a tab that still holds the old state. Clients never seed.
- *Durable before acknowledged:* Hocuspocus acknowledges an update right after applying it in memory and calls `onChange` without awaiting it, so persistence runs in `beforeSync`, which it awaits before it applies. `documents.accept` skips an update the document already holds, and refuses before the append one that does not decode to its end, holds anything but text put into or taken out of the root `content` text, names a client twice, or would leave structs waiting for something the document lacks (stateless `refused` `invalid`), and one that would take the text past `maxBytes` (`too-large`). It then calls `store.append`, which checks that the link is live at that epoch, bumps `seq` and records the editor and `lastEditAt` in one script, and applies the update; Hocuspocus's own apply is then a no-op and its acknowledgement follows. 已儲存 therefore means "in the store". An update that inserted `\r` or NUL is followed by one of the server's own that takes it out. `not-live` sends `released` and closes the document for everyone on it; a store failure closes the socket with 1011, and the provider reconnects and sends what it holds.
- *Server writes* (`write`, `append`, `mergeIn`, `merge`) run on a per-document queue: the update is built on a clone, appended, then applied, so a failed append leaves the document untouched and never surfaces later. A revision is `t:<sha256 of the text>`, which survives reloads and epochs. Each process keeps, per link, a ring of the texts it handed out (64 texts or 16 MiB, newest kept); a write whose base is neither the current text nor in the ring is `LiveStaleError`, and otherwise `rebaseLiveText` (core `live-text.ts`: a character-level three-way rebase on diff-match-patch with a 100 ms timeout) applies it over the typing since, or answers a conflict, which is `LiveStaleError` too. The ring is cleared when everyone has left and on release or discard. `merge` runs `rebaseLiveText(base, current, text)` on the same queue, in the writer's name (`documents.edit(…, merge)`): a conflict, or a diff that ran out of time, takes nothing, a text the note already holds is applied without an edit, and the store's answer for a repeat is returned without appending or applying anything.
- *Compaction* (`onStoreDocument`: debounced 2 s, at most 10 s, and on unload and shutdown) encodes a new state from the store's state plus the log entries it read, and `compact(id, epoch, gen, count, …)` trims exactly those entries if `gen` is unchanged; a refused compaction is logged by id and retried later. Any number of processes may compact, and none drops another's entries. `contentHash` is stored with the `contentSeq` it describes; a row uses it only when `contentSeq === seq`, and otherwise reads and compacts the document.
- *Catch-up:* every `pollMs` (5 s) a document with sockets compares the link's `seq`, `gen`, `live` and `epoch` with what it holds and applies the new log entries; a released link or a newer epoch sends `released` and closes its sockets. Reads, rows, writes and opens catch a held document up on demand, and `detail` reads text and sequence from the store, so `leaseRead(seq, hash)` and `release(expect: { seq })` are exact.

**Socket** (`socket.ts`). `POST /api/live/socket-ticket { notebookId, path }` is for a signed-in writer (`canWrite`) of a covered repository whose editor is builtin, for a note that is already live (409 `code: 'not-live'` otherwise; 400 `not-live` for a framed repository); read-only grants and signed-out requests are refused (403). A ticket is 32 random bytes in base64url; the store keeps its sha256 for 60 s with the repository, link, epoch, document, editor and display name, and `takeTicket` makes it single use. Authentication refuses with `permission-denied` (no ticket, or a malformed, unknown, used, expired or other-document one), `not-live` (released or reopened since, or no longer covered), `busy` (50 connections on the document, or 200 documents loaded), or `unavailable` (the store failed, or shutdown began); the provider retries after none of them. An editor's key is `person:` or `agent:` plus the lower-cased verified email, else `<realm>:<userId>`, and its name is the author's name, else `<realm>:<userId>`; nothing of it comes from the client. Awareness: a connection speaks for the first Yjs client id it sends a state for (another person's id is never taken; the same person's is handed over); `user` is overwritten with `{ name, color }`, the colour a hue from the person key; a state over 4 KiB is dropped. Stateless messages are `{ "type": "released" }` and `{ "type": "refused", "reason": "too-large" | "busy" | "invalid" }`; a released or refused document closes with code 1000 while the socket stays open, and a socket without a document is closed by the 30 s idle timeout. At most `maxUnseated` (100) sockets without a document stay open, `maxUnseatedPerAddress` (10) of them from one address (`socket-address.ts`: the last `X-Forwarded-For` entry from a loopback or private peer, else the peer); an upgrade past either answers 503. A socket open for `socketMs` by the adapter's clock is closed with 4000 `Live ticket renewal` on the next beat, and an update or sync step it sends past that closes it the same way, unstored, so the tab must show a live session again for a fresh ticket.

**Activity, release and epochs** (§5.5, §7). Each process writes one presence entry per document: at once when someone connects or leaves, otherwise every 15 s when activity changed, and again when the entry is 30 s old; it expires 90 s after its last write, so a crashed process stops counting. Activity is a connection's open, an update that added something, and an awareness change apart from `user`. `activeEditors` counts the distinct people, across processes, active within `idleMs` (10 min), so an idle open tab does not hold a note overnight. `release` answers `not-synced`, then `changed`, then `active`, then the store's sequence check, and first waits for this process's own presence write, so a tab that just closed does not count. **Release on leaving** (owner decision on cf16-F006): when the last seat of this process leaves a document (not a socket closed for renewal, nor at shutdown) and nobody of this process came back within `leaveMs` (5 s, so a short loss of the network does not end the session), the adapter releases the note without a commit if its text is still its `base` (nobody typed, or the typing was undone) and nobody is active: it takes the lease, syncs at that base and releases, so neither the lists nor a Git write are held off; a note someone typed in waits for the idle check-in, and any refusal or failure leaves the note to it; `discard` answers `changed`, then `active`. A reopened link starts epoch + 1: tickets name one epoch, and loading, authentication and every append refuse any other, so a tab of an earlier checkout can never write into the reopened note. A deployment runs one app process. Two over one store, as in a deploy overlap, never lose an acknowledged update: `detail` catches up from the store, the lease serializes check-ins, and a check-in from either commits the union. People on different processes see each other's typing within a poll (5 s), not keystroke by keystroke.

**Limits** (`BuiltinLiveLimits`, defaults): `maxBytes` 5 MiB of live text (`LIVE_MAX_BYTES`; checkouts and server writes throw `LiveTooLargeError`, 413), `maxPayload` 8 MiB per WebSocket message (`ws` closes with 1009), `maxDocuments` 200 loaded per process, `maxConnections` 50 per document, `maxAwarenessBytes` 4096, `idleMs` 10 min, `leaseMs` 5 min, `ringTexts` 64, `ringBytes` 16 MiB, `pollMs` 5000, `beatMs` 15 000 (pings and changed presence), `shutdownMs` 15 000, `socketMs` 10 min (a socket's life; see Socket), `leaveMs` 5000 (how long a document stays without a seat before a note nobody typed in is released). A ticket lives 60 s.

**Web** (§8). `NoteEditor` opens `LiveCollabEditor` (`components/live/`) for a repository whose `live.editor.kind` is `builtin` and `LiveEditorFrame` otherwise. It creates a `Y.Doc` and a `HocuspocusProvider` on `ws(s)://<host>/live/socket` whose `token` posts `/api/live/socket-ticket` on every connect, and mounts `LiveMarkdownEditor` with `collab` (y-codemirror.next's `yCollab` and its undo manager in place of `history()`, no `content` sync between views) after the first sync. The bar shows 「N 人編輯中」 from the distinct awareness names; 已儲存 when nothing is unsynced, 未儲存 while something is, and 離線 while disconnected, except after a 4000 close, which reads as connecting until the next close or sync; and 「立即簽回」, enabled only when connected with nothing unsynced, which destroys the provider before it posts `/api/live/checkin`. `beforeunload` warns while something is unsynced. On `released` (or a ticket answer of 409 `not-live`, or a ticket for another epoch's document) a tab with nothing unsynced takes the checked-in path; one with unsynced text merges it into the note (see [Collab-first and offline handover](#collab-first-and-offline-handover-web)), and its `Y.Doc` is destroyed, never merged into the new epoch. Only where the adapter has no `merge`, or the note is gone, does it show 「此筆記已簽回；你離線時的修改沒有存入。」 with 「複製我的版本」, 「下載」 and 「關閉」. `refused` shows the size or busy notice. The Vite dev server proxies `^/live/` with `ws: true`. `MYGITNOTES_LIVE_DEV_EDITOR=builtin pnpm exec tsx scripts/dev-live-memory.ts` runs the dev composition with `builtinLiveNotes` over a memory live store, the upgrade wired on its server, and a second writer `dev2` (`/dev/as/dev2`) beside `dev` and `reader` for a two-person check.

### Collab-first and offline handover (web)

[collab-first spec](../../specs/2026-11-16-collab-first-self-host/spec.md) A1–A3, A7.

- **Which editor opens** (`useLiveEdit`). Where the repository's editor is builtin, zoom and a Focus pane (the phone's note screen is one) check a writer's note out once per arrival and show `LiveCollabEditor`, with no 編輯. While `navigator.onLine` is false, or the checkout or ticket request fails with a network failure (`isNetworkFailure`), they show the direct editor on a browser draft under 「離線：修改先存在這台裝置，連線後會自動併入」 instead; that editor switches to collab only through the draft's handover, never on a short drop. It tries again not only on `online` but when a live request gets through after one failed for want of a connection (`lib/live-reachability.ts`), when the page shows again, and on a timer (5 s doubling to a minute), since a request can fail while the browser counts itself online and no `online` follows (A3.2.1, cf16-F007). A framed editor keeps 0.19's 編輯, and graph cards and compilation sections keep 編輯, which opens zoom. A split view in a Focus pane opens zoom, as in 0.20.2. `?edit` still checks the note out and leaves the address; in a collab-first repository a Focus pane opens it in place instead of in zoom.
- **Badge and list lock** (`LiveBadge`, `liveActionLocked`). Every note a writer opens is checked out, so 「編輯中」 shows only when `activeEditors > 0` or `LiveNoteState.changed` (the live text differs from Git's); a note only viewed shows none and is released without a commit as soon as its last editor leaves. List, bulk and status actions (A7 "keep 0.20's lock") are refused only on a note that shows the badge, or any checked-out note of a framed editor (`LiveDrafts.releasesUntouched`); should a note without the badge still be checked out, the server refuses the write with 409 `checked-out`.
- **File actions from the collab editor** (A7, `fileActions` of `useLiveEdit`). While the editor holds typing the server has not stored (未儲存, kept typing not merged yet, or a merge under way) they are refused with 「還有修改沒存入，等編輯器顯示「已儲存」再移動、重新命名或刪除。」, so the commit never leaves that typing out nor strands it under the old path (cf16-F003). Otherwise move, rename and delete close the editor, post `/api/live/checkin`, and run against the revision the check-in answered once the note is released; a note no longer live runs at once. A check-in that others' editing holds off refuses with 「N 人編輯中，無法移動／重新命名／刪除」 and opens the editor again; a refusal after a commit is still said in the editor the workspace refresh mounts.
- **Unsynced typing** (A3.1, `lib/live-unsynced.ts`). While the server has not stored a tab's typing, each editor session keeps, under a random owner of its own (two tabs, or zoom over its Focus pane, never overwrite each other), the Yjs update of its document (`<link id>.<epoch>`), its text, the text at its last full sync (`baseText`) and a merge id, in IndexedDB (a page-lifetime store without it), debounced 500 ms; the entry goes once the server stored all of it. A session holds a Web Lock on its owner (`lib/live-claims.ts`) while it runs, so a session takes another's entries only once that one ended (a closed or crashed tab, an unmounted editor): entries of the same document it applies before the provider connects, keeping them as its own first, so Yjs sync sends the rest. When that document ended (released, 409 `not-live`, another epoch's document), the session posts `/api/live/merge { base: baseText, text, mergeId, typedIn: { document, update } }` first (`baseText` is the text at the session's first sync, though the connect's own step still waits on its acknowledgement): merged, it opens the note with the text in it; a conflict goes to `onMergeConflict`, which stages it as a `WorkingNote` blocked `live-merge-conflict`, and the note opens as it is now with 「比對」, 「複製我的版本」 and 「捨棄我的版本」. A note has one such draft and nothing is staged over it (`stageWorkingNote` throws, cf16-F002): offline the direct editor stays read-only while it waits, and a second conflicting merge is offered to copy or download, its entry kept until the person leaves it. Offline meanwhile, the kept text shows read-only with 離線. When `online` fires before the socket's close lands, the editor connects again once the close comes, so the tab does not stay offline. The offline screen (`ConnectionState`) lists kept live typing beside drafts.
- **Drafts going online** (A3.2, `useLiveHandover`, `lib/live-handover.ts`). When the workspace loads online, when `online` fires, when a live request gets through after a network failure, and when the page shows again, each draft of a covered note that is not a deletion and not blocked is handed over, one tab at a time per note (a Web Lock; the tab reads the draft again under it and settles it before letting go, so two tabs never file a note made offline twice): a draft with a base is merged with `/api/live/merge`, its base the Git file at the draft's revision when that file holds the draft's base (else both sides serialized at one stamp), `mergeId` from the scope, path and text; a draft without a base (a note made offline) is created pending through `/api/live/new` with its text as the template body, so its first check-in files it instead of discarding it as an empty draft; the pending note made for a draft whose merge has not landed is kept in localStorage, so any tab's retry merges into it. A draft is cleared only once the merge is stored; a conflict keeps it blocked with the notice; a failure keeps it for the next time. An open direct editor on the draft is read-only while its handover runs, and opens the collab editor afterwards. A manual commit (`useWorkingNoteCommit`) sends drafts of notes that are live now through the same merge and commits the rest; deletions and notes the editor does not cover keep the manual commit.

**Testing.** `…/testing/live-store-contract` (`liveStoreContract(name, makeStore)`) is the behavior every `LiveStore` keeps, and `…/testing/builtin-live-notes` (`builtinLiveNotesWithHooks(options)`) is the adapter with the `type` and `setActive` hooks, for running `liveNotesContract` over an edition's own wiring. The Redis cases of the store, adapter, check-in, two-process and socket tests run only with `MYGITNOTES_TEST_REDIS_URL` (a throwaway Redis; the release workflow's test job sets it) and skip without it; each file takes its turn on the server (`redis-test-turn.ts`), because two store tests briefly set `maxmemory-policy allkeys-lru`. `apps/local-server/tests/live-env.test.ts` starts `startServer()` against a stand-in for GitHub behind `fetch`: its refusals and the unset case always, and with `MYGITNOTES_TEST_REDIS_URL` two signed-in people typing over real sockets, the idle sweep committing with the first editor's stored token, the fallback to the second editor's, and the cache in its own Redis database.

## Self-hosted runtime

The [Dockerfile](../../../Dockerfile) builds the web application and runs the compiled Express server as the `node` user. `HOST` defaults to loopback for direct startup and is set to `0.0.0.0` inside the image. The local-source Host and Origin checks remain active; `compose.local.yaml` binds an existing workspace checkout at `/workspace` and publishes only a loopback port.

Note pages come from query routes shared by both sources: `/api/notes/query` (notebook, folder, tag, status, visibility, text and sort filters, cursor pages, optional content, or a full path list), `/api/notes/facets`, `/api/notes/lookup`, `/api/notes/agenda` and `/api/notes/graph`. `NoteCatalog` is the read model behind them: `workspaceCatalog` joins one `RepositoryCatalog` per repository of the request's workspace. `parseNoteQuery` and the query functions live in `packages/core/src/note-catalog.ts`, and filtering, sorting and serialization are shared with the browser through `note-query.ts`. Read routes accept the `revisions` the browser is working from (a JSON `RevisionSet`, one commit per repository) and answer 409 with `staleRepositories` when a branch head has moved (a mismatch with the cached head is rechecked against the uncached head first, since another server instance may have committed), so a screen never mixes two commits of one repository and a request cannot steer reads at arbitrary history. Answers carry the `revisions` of the repositories they read. A note is identified by its notebook and path (`NoteRef`, keyed by `noteRefKey`): `/api/notes/lookup` takes `notes: NoteRef[]`, path selection answers `notes: NoteRef[]`, and browser drafts are keyed the same way, so equal paths in two repositories stay distinct.

A file `move` (`POST /api/files`, `FileCommand` in `packages/core/src/file-manager.ts`) is planned from the snapshot the server reads, so it needs no `revision` from the browser (a named one must still be current, as for every other command) and refuses a taken destination itself. It also refuses a name that another file or folder already has in different letter case or Unicode form (`foldName`: NFC, then lower case), its own included (`differsOnlyInCase` in `packages/core/src/case-collision.ts`): on macOS and Windows both names are one entry, so the write would land on the other file and the move would then delete it. A rename whose new file name only folds to the old one keeps the file and retitles it in place (`planRelocation`). Folder moves and deletes (`planFolderChange`, each relocated entry), new files and folders, and on a hosted repository a new note and an image move refuse such a name too, since a checkout on those systems could not hold both. A rename sends the new `title` with the move: `planFileChange` retitles the moved note in the same write (local) or the same commit (hosted) by the rules of `retitle` in `packages/core/src/note-title.ts`, which the browser applies to a never-committed draft; a compilation keeps its name in its own file and sends none. Links that name the moved file are rewritten by `relocateMovedLinks`, which parses only the notes whose text names the moved file or folder (the notes that move with it, and any note holding a `/api/files/raw?` link, always are). The browser's `useNoteMove` closes the dialog once the move returns, then reads the workspace again in the background; while the move runs, `beginNoteMove` tells an editor open on the old path not to report its disappearance as a conflict, and the unsaved and conflict drafts kept for the old path, and the Focus tabs of this browser's (current) Focus, follow the note.

Remote readers cache notes and their per-notebook indexes in the session Redis, or in the cache's own Redis where `MYGITNOTES_CACHE_REDIS_URL` names one, keyed by repository and Git object id with a 30 day lifetime, falling back to a process-local cache when Redis is absent. Cache failures end the request rather than silently reloading from the platform.

`compose.yaml` runs the remote-source application with its own Redis service on an internal network. Redis persists AOF data in `redis-data`; only the application HTTP port is published. Encrypted records go through a `RecordStore` (`apps/local-server/src/record-store/`): `SealedRecordStore` seals values, expires them, lists grants and orders credential locks over a raw `RecordBackend`. `createRecordStore` chooses native Redis via `REDIS_URL`, then the existing Redis REST configuration, then a local encrypted session directory outside Vercel. Native Redis reuses connections, bounds connection/command waits, and propagates errors; a later request reconnects after a failure. Session/grant keys, encryption, TTLs, indexes, and credential refresh locks use the same operations across both Redis transports.

See the [deployment guide](../../deploy.md#docker-compose-with-a-remote-repository) for volumes, OAuth callbacks, reverse proxies, and updates.

## Slide notes (contour-deck)

A note with `type: slide` in its frontmatter is a deck ([spec](../../specs/2026-11-12-contour-deck/spec.md)); `isSlideNote` (`apps/web/src/lib/slides/note.ts`) is the test. Every slide note is read by contour-deck's headings mode (`SLIDE_STRUCTURE`, `headings`: `---` a block, `##` a slide, `###` a page); neither `slideOptions.engine` nor `slideOptions.structure` is read. The code is in `apps/web/src/lib/slides/`:

- `directives.ts` writes the six slide directives (`:::summary`, `:::build`, `::vertical`, `::block`, `::slide`, `::background`). What a directive means is contour-deck's to say: each is handed to `remarkDeck` (`contour-deck/remark`, the only part of contour-deck in the main bundle) as the node remark-directive would have parsed, and the answer is the marker element `rehypeDeck` reads (with the `data.hChildren` a `::background` carries: its still and credit) or the message of the refusal. `renderNote` takes `{ slides: 'preview' | 'deck' }` as its last argument (`NoteRenderOptions`; `createNoteRenderer`'s `renderNote` takes it too): `preview` draws labelled notes, numbered steps, labelled dividers and headings and an error box for a refused directive (`::vertical` among them), in classes only (`slide-notes`, `slide-build`, `slide-build-step`, `slide-break`, `slide-heading`, `slide-block-title`, `slide-anchor`, `slide-background`, `slide-error`; no inline style, no data attribute but `data-type` and `data-label`); `deck` writes the markers themselves and throws a `SlideDeckError` with the line. Without the option a note keeps the general rendering, in which `:::build` is its content and `::block`, `::slide` and `::background` draw nothing. `qrcode.ts` draws `:qrcode`/`::qrcode` (written by `directives.ts` as a link inside a `data-qrcode` element) on a canvas once the HTML is mounted (`hydrateQrCodes`, lazily importing `qrcode`: `NoteHtml`, the editor's directive widgets and the played deck call it); the live editor draws both forms as widgets (`live-markdown/qrcode-widgets.ts`). `qrcode-edit.ts` is the `qrcode` format of `formatMarkdown` ("Turn into QR code": toolbar, Mod+Shift+L, and the palette command, which reaches the focused editor through `format-request.ts` events); it writes `url=…` so that remark-directive and `parseDirectiveAttributes` read the same string, and refuses text that cannot be written that way. `transformDirectives` skips fenced and indented code blocks for every note (`fencedCodeLines`, `indentedCodeLines`), and so does `findDirectiveBlocks`.
- `structure.ts` is the one place that numbers blocks, slides and pages and names the steps of a build: `HeadingStructureReader` is told the top-level headings, the notes, other content and each `---` in document order and answers the block each `---` ends and the slide and page each `##` and `###` heads, by the rules of contour-deck 0.3.1's headings mode. The rendered preview feeds it from the DOM (`labelSlidePreview`), the live editor from the document (`editorSlideStructure` in `components/live-markdown/slide-structure.ts`, which also carries the boolean `slideNote` facet the editor's decorations read; the live editor's `slides` prop sets it). `remarkDeck` and `rehypeDeck` are both given `SLIDE_STRUCTURE`.
- `deck.ts`, `deck-runtime.ts` and `deck.css` load on the first Play, through `import()` in `components/slides/SlideDeck.tsx`: `readDeck` parses the sanitized `deck` HTML, turns it into hast (`hast-util-from-dom`) and runs contour-deck's `rehypeDeck` on it, `buildDeck` turns the result into DOM (`hast-util-to-dom`), and `openDeck` gives each page the `prose-custom` class, draws mermaid diagrams and PDF figures on the deck's elements, and calls `createDeck` with `url: false`, no `remote`, and English labels when the app is in English. `deck.css` sets contour-deck's `--ct-*` colours from the app's theme tokens on `.ct-app` and sizes a page's headings, lists, tables and code against the stage.

The New note menu lists a notebook's own templates (the manifest's `notebooks[].templates`, then the Markdown files of its `.templates/` folder, listed by `/api/templates` and rendered by the workspace's `/api/templates/render` with the reader's date and time), then the app's built-in ones (`apps/web/src/lib/builtin-templates.ts`), whose ids start with `builtin:`, which a notebook's template id cannot, then Manage templates. A read-only notebook shows no New button and no New menu, in the toolbar or in the phone navigation, so it offers neither templates nor Manage templates. `@mygitnotes/core/note-template` holds the template rules without file access (the `template:` block, `{{name}}` placeholders, rendering, the path pattern, `noteFromTemplate` for callers that fill by name), so the page fills a template that is still a working change itself; `templates.ts` reads them from a worktree and `RemoteSource.templates` from a snapshot, both keeping the parsed list by the content of the template files (see Note templates in the MCP document). A note created from a notebook's template carries `template: <id>` in its frontmatter (`useCreateNote` for the New note menu, `noteFromTemplate` for `save_note` and the web chat agent; a built-in template leaves none), and `/api/templates` dates each template's `lastUsed` from those notes. The page asks for a notebook's templates in one query keyed by the repository revision (`noteTemplatesOptions`), which the New note menu and Manage templates share through `useNotebookTemplates`; a local save, rename or delete invalidates it with the note queries, and a remote one is overlaid as a working change until its commit changes the revision. A `.templates/*.md` file is no note (no index, query, search or folder lists it), but the note routes read, save and commit it by path (`templateFileId` is the one dot-path allowance in `RemoteSource.note`, `save` and `commitChanges`, `classifyResource` answers `template`, and `lookupNotes` falls back to the catalog's `template`), so the ordinary editor edits it in zoom; `isTemplate` in `App.tsx` keeps it out of every Focus pane. `useCreateNote` fills a built-in template in the browser from the i18n strings (`template.slides`, `template.slides.body`), with no title in its metadata, so the heading names the note. The one built-in template is **Slides**: `type: slide` with `slideOptions.engine: contour` and `structure: headings`, both of which a blog needs to read the note as the app does.

No splitting rule is written in this repository. `deck-parity.test.ts` builds the fixture decks (`fixtures/headings.md` and `fixtures/kicker-builds.md`) with a blog's chain given `structure: "headings"` (unified, remark-directive, `remarkDeck`, `rehypeDeck`; devDependencies used by the tests only, under `lib/slides/testing/`) and with ours, and the two decks must agree; `structure.test.ts` and `slide-structure.test.ts` hold the labels to the same decks. Run them first when contour-deck is upgraded.

## Installable app and offline shell

The web build is an installable app (`apps/web/public/site.webmanifest`: `id`, `scope` and `start_url` are `./`, so the app works under a base path; any and maskable icons) whose service worker keeps the app shell, so it opens offline. `serviceWorkerPlugin` (`apps/web/pwa/service-worker-plugin.ts`, built into `vite build` only) writes `sw.js` beside the bundle from `src/pwa/sw.ts`, with the build's file list inlined: `index.html`, the entry bundle, the chunks it imports or starts loading at once (the workspace chunk) with their stylesheets, the web manifest and the brand icons. Every other built file under `assets/` and the Google Fonts files are kept the first time they are fetched; each build names its shell cache by a hash of that list, and activation deletes the caches of other builds and runtime files the new build no longer has. The page registers the worker only in a production build that ran the plugin (`__SERVICE_WORKER__`), so `pnpm dev`, tests and a host that does not ship `sw.js` register nothing; an edition's own Vite config adds the plugin (`shell` names a renamed entry page) and must serve `sw.js` with `Cache-Control: no-cache` (the local server does, `web-static.ts`).

`routeRequest` (`src/pwa/sw-routing.ts`) decides every request and is the only place that does: a page load inside the scope goes to the network first and falls back to the cached shell only when the network fails or answers 5xx (a slow answer is waited for: the cached shell is the previous build, whose lazy files a deployment removes; `navigateWithShell`, `src/pwa/sw-navigate.ts`); built files and icons are answered from the cache; non-GET and ranged requests, `/api`, `/mcp`, `/raw-assets` and `/r2-assets`, each also as the bare path (sign-in and its callbacks, downloads, notes data), the worker file, other origins (except the Google Fonts hosts) and anything outside the scope are never touched or kept. Notes are not cached for offline reading. A newer worker installs but waits: the page shows "A new version is available" (`UpdateNotice`, `src/pwa/update-store.ts`) and only its Reload button posts `SKIP_WAITING` and reloads once the new worker controls the page, so a deployment never swaps the app under an open editor. Every tab that showed the notice hears the swap (`controllerchange`), so after one tab applies it, Reload in another tab reloads at once. If a lazy file is missing anyway (an open tab of an older build after a deployment), the `vite:preloadError` handler (`src/pwa/preload-error.ts`) reloads the page once, guarded by sessionStorage. Offline, the shell opens and the workspace fails to load; `ConnectionState` then says the app is offline, lists the unsaved drafts of the repositories this session last opened, and the live typing kept in this browser (`offlineDrafts`; the opened scopes are recorded in localStorage by the workspace and cleared on sign-out, and with no record the screen only counts drafts, so another account's titles are never shown), and retries by itself when the connection returns.

`applyTheme` keeps the `theme-color` meta in the active theme's background (index.html ships one tag per colour scheme for the first paint). An installed iOS app uses status bar style `default`, so the system draws the bar in that colour above the page and the page never sits under it (the top inset is 0). `src/pwa/pwa.css` defines `--safe-top`, `--safe-right`, `--safe-bottom` and `--safe-left` (the `env(safe-area-inset-*)` values) and `--pwa-notice-lift` (the update notice's lift from the bottom edge: the bottom inset, plus the 64px bottom navigation on a phone); layouts pad by these rather than repeating `env()`.

The worker file is the one file that must never be answered with the app page. The local server and `vercel.json` answer a missing `/sw.js` and a missing `/assets/*` with 404. To retire the worker (stop offline support, or move off this host), ship a `sw.js` that unregisters itself instead of removing the file: `self.addEventListener('install', () => self.skipWaiting()); self.addEventListener('activate', () => self.registration.unregister().then(() => self.clients.matchAll()).then(clients => clients.forEach(client => client.navigate(client.url))));`, and delete the page's `registerServiceWorker()` call in a later release, once installed copies have updated. Deleting `sw.js` outright leaves every installed app on its last cached build, because the update check finds a 404 and keeps the old worker.

## Notebook default sort

A manifest notebook accepts an optional `default_sort: { field, order }` next to `default_view`, for
example `default_sort: { field: metadata.date, order: desc }`. `field` is `updated`, `created`, `title`,
`status`, or `metadata.<key>` for a frontmatter key of letters, digits, `_` and `-`; `order` is `asc` or
`desc` and defaults to `desc`. Anything else (a non-mapping, an unknown field or key, an unknown order)
fails config validation with a `ConfigValidationError` naming the notebook, and the validated config keeps
the value so a manifest save writes it back.

`sortNotes` in core (`packages/core/src/note-sort.ts`) orders by `metadata.<key>` for every list: the web
list, flat, card and Kanban views and `GET /api/notes/query` (`sort=metadata.<key>`) share it. A value that
is a `Date` or an ISO date or timestamp string (`2026-11-14`, `2026-11-14T09:30:00+08:00`) compares as a
point in time, any other string, number, boolean or list (joined with `, `) as natural, case-insensitive text
as titles do, and a date sorts before text where one list holds both. A note without the key, or with a blank
or non-scalar value, sorts last in both orders. Ties, including notes that all lack the key, fall back to
`updated` newest first, then title. The MCP `list_notes` order is not affected.

The web app resolves a notebook's sort (`useNoteSort(notebookKey, notebook)`, `resolveNoteSort`) in this order:
a `sortField`/`sortOrder` in the URL, the sort the person chose for that notebook (saved per notebook key in
`github-notes:sort:<notebookKey>`), the notebook's `default_sort`, the browser-wide sort saved before notebooks
had their own (`github-notes:sort-field`, `github-notes:sort-order`, now only read), then `updated` newest first.
Choosing a sort saves it for the current notebook only, and switching notebooks drops the URL sort. The sort menus
(toolbar, phone filter sheet, mobile list sort, Kanban board and columns) list `metadata.<key>` in both orders,
labelled by its key, when the notebook's `default_sort` or the sort in force names one.

## Notes, files and `exclude`

A note is a Markdown or text file (`.md`, `.markdown`, `.mdx`, `.txt`) in a notebook, outside its assets folder, dot
names, `node_modules`, `dist`, `build`, `AGENTS.md` and `docs/agent`. Every other file of a notebook is a file: it is in
no note list, search, catalog, graph, agenda or MCP listing, and `classifyResource` names its kind from the extension or a
well-known name (`fileKind`, `packages/core/src/file-kind.ts`): `text_file` (sql, yml, json, csv, ts, js, py, sh, xml, log,
Makefile, Dockerfile and the like), `pdf_file`, `html_file`, or `other_file`.

A relative link from a note to such a file opens it where the note shows, in the web app's read-only file viewer
(`WorkspaceLinks`), which reads the file through `/api/files/read` and shows text as text; a file that is not text, a PDF
or a page has an *Open original* link to `/api/files/raw`. A link never reaches a path the notebook does not reach: the
web app refuses dot names, dependency and build folders, agent files and assets before asking, and the file manager keeps
its own checks. The raw routes (`/raw-assets/<path>?notebook=`, `/api/files/raw`) send a text file as `text/plain;
charset=utf-8` whatever its extension names, a PDF as `application/pdf` under `default-src 'none'` (the browser's PDF
viewer refuses a document under the `sandbox` directive, and the bytes are only ever read as a PDF), and a page or any
other file under `default-src 'none'; sandbox`, so a page runs no script and shares no origin with the app
(`rawFileHeaders`). Every one of these policies ends in `frame-ancestors 'self'`: the route lifts `X-Frame-Options` so
the app's viewers can show a file, and only the app's own pages may frame it. Plain text for a file that looks like a
page, and a PDF outside the sandbox, are safe only while the browser may not guess another type, which the app-wide
`X-Content-Type-Options: nosniff` forbids; the raw-route tests assert that header on text, PDF and page answers. Local
and remote (GitHub, GitLab) workspaces share one router (`createFileManagerRouter`), so both follow the same rules and
checks.

The manifest may list globs of paths that are not notes, for a repository whose Markdown is generated output or
analysis rather than notes:

```yaml
exclude:            # every notebook
  - "**/analysis/**"
  - "**/*.draft.md"
notebooks:
  - id: docs
    root: docs
    exclude:        # this notebook, after the workspace's
      - "reports/**"
```

Globs are matched, case-sensitively, against the path inside the notebook (no notebook root, `/` separators, no leading
`./`), in the dialect of `packages/core/src/path-glob.ts`, which the note shell's glob shares: `**` as a whole segment
crosses folders, `*` and `?` stay inside one name (so `*.md` names top-level files only, `**/*.md` every one), `[ab]`,
`[a-z]` and `[!a]` match one character, `{a,b}` is either alternative, every other character is itself, and a dot name
is matched like any other. A path is excluded when a glob matches it or a folder above it, so `**/analysis` takes
everything under every `analysis` folder. A glob ending in `/` names a folder and is read without it: `drafts/` is
`drafts`, the folder and everything under it. A glob cannot tell a file from a folder, so `a/**` takes what `a` takes
and `*/**` takes top-level files too; `*/*` is what lies inside the top-level folders.

The manifest and the file names of a repository are written by whoever can push to it, so matching is bounded
whatever they hold. No glob becomes a regular expression: a name is matched by a walk that returns only to the last
`*`, and segments by tracking which of them the path has reached, so a pattern costs at most its length times the
path's. What a backtracking matcher would loop on is not in the dialect: extended globs (`!(a)`, `*(a)`, `+(a)`,
`?(a)`, `@(a)`), parentheses, `|`, ranges such as `{1..3}`, escapes, and `**` joined to a name. A glob holds at most
256 characters, its groups expand to at most 64 alternatives of 1024 characters together (`{a,b}{c,d}` multiplies, so
the product is what is capped), and a list holds at most 100 globs. Every path of a notebook is matched against the
workspace's globs and its own together, so those are bounded together too: their distinct expanded patterns (the same
pattern written twice, or reached through two groups, counts once) hold at most 1024 characters, what one glob alone
may expand to. The cost grows linearly with the path: measured worst cases are about a tenth of a second for a thousand
300-character paths against a brace-heavy list, and up to about 0.7 s for a thousand paths 150 folders deep against 200
distinct `**/X` globs (a 51,000-character path about 0.1 s). Lists people write stay far below these.

A glob that is not a string, is blank, begins with `!` or `/`, holds `..`, `.`, an empty segment, a backslash or a
control character, is outside the dialect or past a limit (an unclosed `[` or `{`, a parenthesis, more than 64
alternatives), a list of more than 100, or a workspace list, or a notebook's together with the workspace's, past the
1024 characters makes the manifest fail with a `ConfigValidationError` naming the list, as for any other invalid field. `exclude` and `notebooks[].exclude` are written back as written; the globs a notebook
applies (`NotebookConfig.excluded`, workspace first) are derived on read and never saved.

An excluded path is not a note, an outline or a compilation, and its folders are not note folders, but it stays a file of its
notebook: a link to it opens the file as above, and the file manager lists and reads it. An excluded `.md` is
`text_file` and shown as plain text; its images stay assets. `isNotebookContent` is false for excluded paths and
`isNotebookPath` is true, so every listing, scan, folder walk, shell tool and history path that already asks
`isNotebookContent` follows with no further change. Without `exclude` nothing changes, and `.txt` stays a note.

No note route or note tool takes a file kind (`FILE_RESOURCE_TYPES`), so an excluded path or a `.sql` file is read
through the file routes only, on every kind of workspace. A remote workspace refuses it in `RemoteSource.note` and
`save`; a local one in `/api/notes/read`, save, delete and restore (`assertNote`, `local-notes.ts`) and in the local
MCP server's `read_note`, `save_note` and `delete_note` (`assertNoteResource`), each with `Path is not a configured
note.` and, over HTTP, status 403. The manifest editor shows `exclude` as written and never the derived `excluded`.

## Notebook statuses and visibility

Each manifest notebook accepts an optional ordered `statuses` array, for example
`statuses: [capture, review, published]`. Missing or empty definitions fall back to
`inbox`, `working`, `done`, `archived`. The first entry is the initial status for
new notes; the order also determines Kanban columns. Update definitions through
the local Settings manifest editor or the source repository manifest.

An entry is a bare name or `{ name: review, color: purple, label: … }`, so
`statuses: [capture, { name: review, color: purple }, published]` is valid. `color`
takes a palette name only: `green`, `blue`, `amber`, `red`, `purple`, `teal`, `pink`
or `gray`, each with a light and a dark value in the theme tokens; any other value,
an unknown key, or a repeated name fails config validation. The validated config keeps
each entry as written, so a manifest save writes colors back. Code that needs only the
vocabulary reads names through `noteStatusNames` / `configuredNoteStatuses`.

`label` is what the status is called on screen; `name` stays the value stored in a
note's `status:` frontmatter, in filters, routes and commit trailers (trailers record paths only; the status change a commit's subject or body describes uses the label). A label is one
nonblank string, or a map from a UI language tag to a nonblank string
(`label: { en: In progress, zh-TW: 進行中 }`); a language tag has no surrounding spaces and looks like `en`, `zh-TW` or `zh-Hant-TW`; anything else fails config validation with
the shape it expects. `statusLabel(status, statuses, language)` in core resolves it: the
entry's label for the language (exact tag, then ignoring case, then the primary language
such as `zh` for `zh-TW`), else the built-in name of a default status (`BUILTIN_STATUS_LABELS`:
inbox / working / done / archived in `zh-TW` only; English shows the stored name exactly as written, so `Done` stays `Done`), else the stored name. Web components
read it through `useStatusLabel()` (`apps/web/src/lib/status-color.tsx`), which resolves
against the same `StatusColorProvider` statuses as the dots, and `mergeNotebookStatuses`
merges labels per language across notebooks (the first notebook giving a language wins it; a plain string label counts as every language for its notebook). The status select, the frontmatter status
field, Kanban column titles, the sidebar and graph status filters, the filter chips, the
graph legend when coloured by status, the bulk status menu, the study stage names and the
status change a commit message describes all show the label.

Every status dot resolves through `statusColor(status, statuses)` in core
(`packages/core/src/note-status.ts`). A color the notebook gives wins; then the known
names keep their colors (`done` green, `working`/`doing`/`in-progress` blue, `todo`
amber, `inbox` the theme primary, `archived` muted); any other listed status takes
`purple, teal, pink, blue, green, red, amber` by its position among the custom
(non-known-name) entries of its own notebook's list, so a colour never depends on which
notebooks are listed or in what order; gray is for explicit use only. The theme family
asks the cycle to skip the colour closest to its primary (`statusAvoidColor`, from the
light and dark values in `palettes.ts`: teal for Flexoki, purple for Catppuccin and
Rosé Pine), so no cycled status looks like an inbox. A status that is not listed stays
muted gray. Web components read it through `useStatusDotClass()`
(`apps/web/src/lib/status-color.tsx`), which resolves against the statuses of the
notebooks being listed (`StatusColorProvider`, fed by `mergeNotebookStatuses`, which
resolves each notebook's cycled colours before merging; a name keeps the colour the
first notebook defining it gives, and a colour written in a manifest beats a cycled
one); for a note of a known notebook use
`statusDotClass(statusColor(status, configuredNotebookStatuses(notebook), avoid))`.
Green, blue, amber and red are the theme's `success`, `info`, `warning` and `danger`
tokens; the other four are `--color-status-*` tokens defined in `palettes.ts`.

The browser-safe core note-status module combines definitions with observed note
values. Unknown values extend choices for that notebook; definitions remain
unchanged. Values are case-sensitive and retain their original spelling. Existing
notes retain all metadata, and unassigned notes remain without a status.

The note YAML boolean `hiden` controls visibility. When absent, archived notes
are hidden and other notes are visible. An explicit false keeps even an archived
note visible. UI archive actions set hiden to true; leaving archived sets it to
false. Other status changes preserve manual visibility. The metadata editor also
exposes Hide note. Sidebar Show hidden notes includes hidden notes in List, Card,
Kanban and search, with the choice stored in the showHidden URL query. Direct
note links, repository reads and MCP access still resolve hidden notes. Visibility
is a presentation preference, not an authorization boundary.
