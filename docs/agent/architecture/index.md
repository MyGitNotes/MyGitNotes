# Architecture

MyGitNotes is structured as a TypeScript monorepo using pnpm workspaces.

## Monorepo Layout

- `packages/core`: Core domain models, `.mygitnotes.yaml` (or the compatible `.github-notes.yaml`) schema & parsing, Markdown & YAML frontmatter parsing with exact round-trip preservation, resource classification, and path traversal guards.
- `packages/git`: Guarded Git service operations, Core update engine, and semantic commit message generation (with Gemini Flash-Lite and deterministic fallback).
- `packages/mcp-server`: Stdio Model Context Protocol (MCP) server providing safe note, asset, git, and workspace operations to coding agents.
- `apps/local-server`: Lightweight local HTTP bridge serving workspace APIs and static assets to the frontend web application.
- `apps/web`: Responsive, modern React frontend supporting List, Card, and Kanban views, pure Markdown & plain-text editors, asset manager, and crash-recovery drafts.
- `scripts/`: Cross-platform Node/TypeScript scripts for `bootstrap-workspace`, `update-core`, `migrate-workspace` and `convert-workspace`.

## Core Invariants

1. **Markdown is the source of truth**: Notes are plain Markdown files with optional YAML frontmatter. No proprietary database or HTML blob becomes authoritative over files on disk.
2. **Boundary between Core and User content**: `core` carries only product source and `main` carries only workspace content (`.mygitnotes.yaml`, notebook roots, assets, workspace Agent settings). The local server runs from a `core` worktree and edits the `main` worktree named by `MYGITNOTES_LOCAL_PATH`; `core` only fast-forwards and never merges into a content-only `main`. Fork-model workspaces whose `main` still carries the product merge Core with workspace Agent paths restored until they run `convert-workspace`.
3. **Round-trip fidelity**: Updating a note's frontmatter (e.g. changing Kanban column/status) preserves all unknown frontmatter fields and the original markdown text unchanged.

## Configurable sources

`mygitnotes.server.yaml` (or the compatible `github-notes.server.yaml`) selects a local repository, GitHub repository or GitLab project. Without a configured local path, a local source reads the application root only when it holds a workspace manifest (fork model); otherwise startup fails and names `bootstrap-workspace`. Local startup also rejects a workspace whose `schema_version` differs from `SUPPORTED_SCHEMA_VERSION` (now 3, compilations); `migrate-workspace` upgrades it, converting Screen lanes into `*.compilation.yml` files. Compilations are note-shaped files served through the note routes; there is no `/api/screen-page`. Product reference documents under `docs/agent/**` are served read-only from the application root, not from the workspace. Source configuration accepts `MYGITNOTES_*` and legacy `GITHUB_NOTES_*` environment variables.

A workspace is a list of member repositories on one site (`WorkspaceSettings`: `{ site, members, manifest }`; each `WorkspaceMember` has `ref`, `alias`, `default`, `hidden` and, in local mode, `localPath`). There is no home repository: each member's own `.mygitnotes.yaml` (manifest `schema_version: 4`) declares the notebooks it holds, and the default member is where the workspace opens. A deployment's member list comes from `deploymentConfigSource`: the repository the environment or the top-level `source:` names is the default member, and in local mode each worktree `repositories` in `mygitnotes.server.yaml` maps is another member, its alias derived from its repository's name in that order (the derivation phase 1 used, so keys and URLs do not change). Sign-in, `signedIn`, grants and Gists follow `settings.site`, which is known before any repository is reached; agent sessions, the default notebook and `/api/assets` without a notebook follow the default member. Every request resolves its configuration through the replaceable `WorkspaceConfigSource` and its repositories through `WorkspaceRepositories`, which opens each visible member with the signed-in credential (hosted) or its worktree (local), once per request, and reports unreachable ones as unavailable; a signed-out request whose private default repository refuses it fails as a whole, so the page asks to sign in. Revisions, drafts, commits, compilation/Focus/Study files, Agent files and Git status are per repository; one write never spans repositories. See [ADR 0001](../../adr/0001-multi-repository-notebooks.md).

Each repository's manifest is read and saved through `WorkspaceRepositories.manifestOf` / `saveManifest`, by repository id, from the store `settings.manifest(member, inRepository)` chooses (`localManifest` for a worktree, `RemoteManifest` for a provider repository, unless an edition keeps manifests elsewhere). It names the repository (`workspace.title`, else the repository name), says where it opens (`workspace.default_notebook`) and sets the `preferences` of its notebooks. A worktree without a manifest serves no notebook until one is saved (a local source creates it under `notes/`, a mapped repository at its root); a provider repository without one gets one derived from its top-level Markdown folders (`deriveWorkspaceConfig`, `manifest: 'derived'`). A manifest that does not load (YAML or validation error, unsupported schema, a notebook that still uses `source`, which schema 4 removed: `NotebookSourceError`, fixed by `pnpm convert-sources`) makes its repository unavailable (`invalid-manifest`) with the reason, while the other repositories keep working; the repository stays open for `saveManifest` (`handleOf`), so Settings can fix the file. `GET /api/workspace` reports `keyedConfig`, `defaultRepository`, `coreUpdate` and per repository `title`, `defaultNotebook`, `preferences`, `config`, `configRevision`, `manifestError` (with the file's text, or empty text when it cannot be read) and `unavailable`. A symbolic link is never taken for a manifest. `PUT /api/workspace/config` takes `{ repository, configYaml, configRevision }` and answers 409 when that repository's manifest moved: a remote revision is the branch head, a local one a hash of the manifest file (`MISSING_MANIFEST_REVISION` when there is none), checked under the worktree's mutation queue. Settings' manifest editor opens on the current notebook's repository (the default repository's without one) and keeps the person's unsaved text when only a revision moves; a 409 refreshes the workspace and keeps that text, so the next save goes against the current revision. The browser applies a note's repository preferences through `notebookPreferences(notebookId)`; the header shows the title of the shown notebook's repository, and the default repository's on Settings, Agents and all-notebooks pages (`pageRepository`). `files.hide_dotfiles` is obsolete: kept when a manifest sets it, never added. Hosted Core updates act on the deployment's product repository (`productRepository`: `MYGITNOTES_PRODUCT_REPOSITORY` or `product_repository`), not on a workspace repository; without one the `/api/core` routes answer 404 and `coreUpdate` is false, and naming one where each visitor chooses a repository fails at startup.

`RemoteSource` contains shared note, folder, asset, compilation and Study rules. `GitHubSource` and `GitLabSource` implement immutable reads and atomic commits. `createRemoteSource` selects the adapter for HTTP and remote MCP. GitLab supports an HTTPS base URL and nested project namespaces.

OAuth follows the selected provider. Encrypted server records isolate site and account identity. GitLab refresh tokens are rotated under a credential lock and shared by browser sessions and persistent MCP grants. GitHub keeps its existing credential and grant identifiers; short-lived GitHub OAuth app tokens rotate under the same credential lock for persistent MCP grants, while GitHub browser sessions end with their access token.

See the [deployment guide](../../deploy.md).

## Editions and extension points

This repository is the AGPL-3.0 community edition; the private Pro edition includes it as a Git submodule and composes it without editing it ([ADR 0002](../../adr/0002-open-core-editions.md)). The server's composition root is `createApp(base, services)`: an edition may supply the `configSource`, `recordStore`, `sessions`, `workspaceChoices` (left out, a sealed cookie whatever `configSource` is; `null` when each person's repositories live in the edition's `MembershipStore`), `remoteCache`, `piAgent`, the `assetStorage` (which R2 bucket and key prefix each request reaches, with optional `reserve(scope, key, bytes)` and `record(scope, key, deltaBytes)` quota hooks; a non-empty prefix must end in `/`; `envAssetStorage` is the default), the `webDist` it serves, a `publishing` service (`sync({ req, res, repository, notes })`, run beside the Gist push after a commit or save succeeds with the committed notes, deletions excluded; its `PublishSync[]` answer is merged into the commit answer as `published`, a throw becomes an error for each note and never undoes the commit, and without a service nothing changes), an `identity` service (`IdentityService`: who is signed in, the provider token on a site, a grant's token, sign-in options and sign-out; left out, `providerIdentity` signs in with the workspace site's GitHub or GitLab as before; see [identity service](../../specs/2026-10-19-identity-service/spec.md)), `editionSources` (`EditionSources.open(source, { person, request }, cache, scope)` opens the edition's own `{ type: 'edition', platform, repository, branch, label? }` members as a `RemoteSource` without a provider token, for the signed-in person; only the server composes one, so a server file cannot name one and the stdio MCP server and scripts treat it as `unsupported-platform`. Beside it, a provider member of a signed-in person with no credential on the site is unavailable `no-credential` with the identity's message and no provider request, and `/mcp` accepts a grant without a credential when `editionSources` is set; an adapter without a token overrides `RemoteSource.mayWrite()`. `…/testing/memory-edition-source` is the in-memory reference), and a `routes` hook mounted after sign-in and before the workspace routes. `@mygitnotes/local-server` resolves to `src/edition.ts`, which starts nothing, and `@mygitnotes/local-server/testing/record-store-contract` and `…/testing/workspace-choices-contract` are the behavior every record store and every workspace choice store must keep; `…/testing/asset-storage-contract` does the same for an `AssetStorage`. `…/testing/identity-contract` does the same for an `IdentityService`: a person who is signed in may hold no provider token, and the members list, writes and agent grants follow the person while each repository still checks its own access. Every R2 route, the asset handler and the MCP asset tools (`list_assets`, `add_asset`, `delete_asset`, local and remote) read keys through the scope: a key outside the scope's prefix is not found, and MCP uploads are reserved and recorded like the browser's. The `/mcp` body limit is decided after sign-in from the scope too (64 MiB when the storage has a bucket for the caller, else 8 MiB). An upload URL signs the declared `Content-Length`, and `reserve` names the key so an edition can hold a pending row for an upload the browser never confirms; the browser reports the finished upload at `/api/r2/uploaded`, which confirms the key (idempotent: it may repeat, so an edition keeps one row per key) and is when `record` runs, and answers at once without a bucket or GitHub request when the storage has no `record`. A `PiAgent` (`router`, optional `upgrade`) is mounted at `/api/pi` in remote mode too, which stays empty for the community edition because it passes none; the web app asks a remote deployment for an agent session only when a `WebFeature` sets `agent: true`. An agent session starts in an agent workspace, `{ repository, folder }` (folder empty for the repository root; see [agent workspaces](../workflows/workspace-agent-system.md)), and `PiSessionInfo.location` reports it. `createPiAgent({ webTools: true })` gives Pi note tools that edit the working changes of the page holding the panel instead of files (see [web agent tools](../mcp/index.md#web-agent-tools)); `PiSession` and `WebToolError` are exported for an edition that runs its own bridge. A `PiAgent` may leave out `upgrade`, and a `PiSessionInfo.socket` (`{ url, protocols? }`) makes the web panel connect there instead of to `/api/pi/ws` on its own host. ## Self-hosted runtime

The [Dockerfile](../../../Dockerfile) builds the web application and runs the compiled Express server as the `node` user. `HOST` defaults to loopback for direct startup and is set to `0.0.0.0` inside the image. The local-source Host and Origin checks remain active; `compose.local.yaml` binds an existing workspace checkout at `/workspace` and publishes only a loopback port.

Note pages come from query routes shared by both sources: `/api/notes/query` (notebook, folder, tag, status, visibility, text and sort filters, cursor pages, optional content, or a full path list), `/api/notes/facets`, `/api/notes/lookup`, `/api/notes/agenda` and `/api/notes/graph`. `NoteCatalog` is the read model behind them: `workspaceCatalog` joins one `RepositoryCatalog` per repository of the request's workspace. `parseNoteQuery` and the query functions live in `packages/core/src/note-catalog.ts`, and filtering, sorting and serialization are shared with the browser through `note-query.ts`. Read routes accept the `revisions` the browser is working from (a JSON `RevisionSet`, one commit per repository) and answer 409 with `staleRepositories` when a branch head has moved (a mismatch with the cached head is rechecked against the uncached head first, since another server instance may have committed), so a screen never mixes two commits of one repository and a request cannot steer reads at arbitrary history. Answers carry the `revisions` of the repositories they read. A note is identified by its notebook and path (`NoteRef`, keyed by `noteRefKey`): `/api/notes/lookup` takes `notes: NoteRef[]`, path selection answers `notes: NoteRef[]`, and browser drafts are keyed the same way, so equal paths in two repositories stay distinct.

A file `move` (`POST /api/files`, `FileCommand` in `packages/core/src/file-manager.ts`) is planned from the snapshot the server reads, so it needs no `revision` from the browser (a named one must still be current, as for every other command) and refuses a taken destination itself. It also refuses a name that another file or folder already has in different letter case or Unicode form (`foldName`: NFC, then lower case), its own included (`differsOnlyInCase` in `packages/core/src/case-collision.ts`): on macOS and Windows both names are one entry, so the write would land on the other file and the move would then delete it. A rename whose new file name only folds to the old one keeps the file and retitles it in place (`planRelocation`). Folder moves and deletes (`planFolderChange`, each relocated entry), new files and folders, and on a hosted repository a new note and an image move refuse such a name too, since a checkout on those systems could not hold both. A rename sends the new `title` with the move: `planFileChange` retitles the moved note in the same write (local) or the same commit (hosted) by the rules of `retitle` in `packages/core/src/note-title.ts`, which the browser applies to a never-committed draft; a compilation keeps its name in its own file and sends none. Links that name the moved file are rewritten by `relocateMovedLinks`, which parses only the notes whose text names the moved file or folder (the notes that move with it, and any note holding a `/api/files/raw?` link, always are). The browser's `useNoteMove` closes the dialog once the move returns, then reads the workspace again in the background; while the move runs, `beginNoteMove` tells an editor open on the old path not to report its disappearance as a conflict, and the unsaved and conflict drafts kept for the old path, and the Focus tabs of this browser's (current) Focus, follow the note.

Remote readers cache notes and their per-notebook indexes in the session Redis, keyed by repository and Git object id with a 30 day lifetime, falling back to a process-local cache when Redis is absent. Cache failures end the request rather than silently reloading from the platform.

`compose.yaml` runs the remote-source application with its own Redis service on an internal network. Redis persists AOF data in `redis-data`; only the application HTTP port is published. Encrypted records go through a `RecordStore` (`apps/local-server/src/record-store/`): `SealedRecordStore` seals values, expires them, lists grants and orders credential locks over a raw `RecordBackend`. `createRecordStore` chooses native Redis via `REDIS_URL`, then the existing Redis REST configuration, then a local encrypted session directory outside Vercel. Native Redis reuses connections, bounds connection/command waits, and propagates errors; a later request reconnects after a failure. Session/grant keys, encryption, TTLs, indexes, and credential refresh locks use the same operations across both Redis transports.

See the [deployment guide](../../deploy.md#docker-compose-with-a-remote-repository) for volumes, OAuth callbacks, reverse proxies, and updates.

## Installable app and offline shell

The web build is an installable app (`apps/web/public/site.webmanifest`: `id`, `scope` and `start_url` are `./`, so the app works under a base path; any and maskable icons) whose service worker keeps the app shell, so it opens offline. `serviceWorkerPlugin` (`apps/web/pwa/service-worker-plugin.ts`, built into `vite build` only) writes `sw.js` beside the bundle from `src/pwa/sw.ts`, with the build's file list inlined: `index.html`, the entry bundle, the chunks it imports or starts loading at once (the workspace chunk) with their stylesheets, the web manifest and the brand icons. Every other built file under `assets/` and the Google Fonts files are kept the first time they are fetched; each build names its shell cache by a hash of that list, and activation deletes the caches of other builds and runtime files the new build no longer has. The page registers the worker only in a production build that ran the plugin (`__SERVICE_WORKER__`), so `pnpm dev`, tests and a host that does not ship `sw.js` register nothing; an edition's own Vite config adds the plugin (`shell` names a renamed entry page) and must serve `sw.js` with `Cache-Control: no-cache` (the local server does, `web-static.ts`).

`routeRequest` (`src/pwa/sw-routing.ts`) decides every request and is the only place that does: a page load inside the scope goes to the network first and falls back to the cached shell only when the network fails or answers 5xx (a slow answer is waited for: the cached shell is the previous build, whose lazy files a deployment removes; `navigateWithShell`, `src/pwa/sw-navigate.ts`); built files and icons are answered from the cache; non-GET and ranged requests, `/api`, `/mcp`, `/raw-assets` and `/r2-assets`, each also as the bare path (sign-in and its callbacks, downloads, notes data), the worker file, other origins (except the Google Fonts hosts) and anything outside the scope are never touched or kept. Notes are not cached for offline reading. A newer worker installs but waits: the page shows "A new version is available" (`UpdateNotice`, `src/pwa/update-store.ts`) and only its Reload button posts `SKIP_WAITING` and reloads once the new worker controls the page, so a deployment never swaps the app under an open editor. Every tab that showed the notice hears the swap (`controllerchange`), so after one tab applies it, Reload in another tab reloads at once. If a lazy file is missing anyway (an open tab of an older build after a deployment), the `vite:preloadError` handler (`src/pwa/preload-error.ts`) reloads the page once, guarded by sessionStorage. Offline, the shell opens and the workspace fails to load; `ConnectionState` then says the app is offline, lists the unsaved drafts of the repositories this session last opened (`offlineDrafts`; the opened scopes are recorded in localStorage by the workspace and cleared on sign-out, and with no record the screen only counts drafts, so another account's titles are never shown), and retries by itself when the connection returns.

`applyTheme` keeps the `theme-color` meta in the active theme's background (index.html ships one tag per colour scheme for the first paint). An installed iOS app uses status bar style `default`, so the system draws the bar in that colour above the page and the page never sits under it (the top inset is 0). `src/pwa/pwa.css` defines `--safe-top`, `--safe-right`, `--safe-bottom` and `--safe-left` (the `env(safe-area-inset-*)` values) and `--pwa-notice-lift` (the update notice's lift from the bottom edge: the bottom inset, plus the 64px bottom navigation on a phone); layouts pad by these rather than repeating `env()`.

The worker file is the one file that must never be answered with the app page. The local server and `vercel.json` answer a missing `/sw.js` and a missing `/assets/*` with 404. To retire the worker (stop offline support, or move off this host), ship a `sw.js` that unregisters itself instead of removing the file: `self.addEventListener('install', () => self.skipWaiting()); self.addEventListener('activate', () => self.registration.unregister().then(() => self.clients.matchAll()).then(clients => clients.forEach(client => client.navigate(client.url))));`, and delete the page's `registerServiceWorker()` call in a later release, once installed copies have updated. Deleting `sw.js` outright leaves every installed app on its last cached build, because the update check finds a 404 and keeps the old worker.

## Notebook statuses and visibility

Each manifest notebook accepts an optional ordered `statuses` array, for example
`statuses: [capture, review, published]`. Missing or empty definitions fall back to
`inbox`, `working`, `done`, `archived`. The first entry is the initial status for
new notes; the order also determines Kanban columns. Update definitions through
the local Settings manifest editor or the source repository manifest.

An entry is a bare name or `{ name: review, color: purple }`, so
`statuses: [capture, { name: review, color: purple }, published]` is valid. `color`
takes a palette name only: `green`, `blue`, `amber`, `red`, `purple`, `teal`, `pink`
or `gray`, each with a light and a dark value in the theme tokens; any other value,
an unknown key, or a repeated name fails config validation. The validated config keeps
each entry as written, so a manifest save writes colors back. Code that needs only the
vocabulary reads names through `noteStatusNames` / `configuredNoteStatuses`.

Every status dot resolves through `statusColor(status, statuses)` in core
(`packages/core/src/note-status.ts`). A color the notebook gives wins; then the known
names keep their colors (`done` green, `working`/`doing`/`in-progress` blue, `todo`
amber, `inbox` the theme primary, `archived` muted); any other listed status takes
`purple, teal, pink, blue, green, red, amber` by its position among the custom
(non-known-name) entries of its own notebook's list, so a colour never depends on which
notebooks are listed or in what order; gray is for explicit use only. The theme family
asks the cycle to skip the colour closest to its primary (`statusAvoidColor`, from the
light and dark values in `palettes.ts`: teal for Flexoki, purple for Catppuccin and
Rosé Pine), so no cycled status looks like an inbox. A status that is not listed stays
muted gray. Web components read it through `useStatusDotClass()`
(`apps/web/src/lib/status-color.tsx`), which resolves against the statuses of the
notebooks being listed (`StatusColorProvider`, fed by `mergeNotebookStatuses`, which
resolves each notebook's cycled colours before merging; a name keeps the colour the
first notebook defining it gives, and a colour written in a manifest beats a cycled
one); for a note of a known notebook use
`statusDotClass(statusColor(status, configuredNotebookStatuses(notebook), avoid))`.
Green, blue, amber and red are the theme's `success`, `info`, `warning` and `danger`
tokens; the other four are `--color-status-*` tokens defined in `palettes.ts`.

The browser-safe core note-status module combines definitions with observed note
values. Unknown values extend choices for that notebook; definitions remain
unchanged. Values are case-sensitive and retain their original spelling. Existing
notes retain all metadata, and unassigned notes remain without a status.

The note YAML boolean `hiden` controls visibility. When absent, archived notes
are hidden and other notes are visible. An explicit false keeps even an archived
note visible. UI archive actions set hiden to true; leaving archived sets it to
false. Other status changes preserve manual visibility. The metadata editor also
exposes Hide note. Sidebar Show hidden notes includes hidden notes in List, Card,
Kanban and search, with the choice stored in the showHidden URL query. Direct
note links, repository reads and MCP access still resolve hidden notes. Visibility
is a presentation preference, not an authorization boundary.
